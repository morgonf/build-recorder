# build-recorder — модель угроз и граница гарантии «собрано из исходников»

Статус: живой документ. Отражает состояние ветки после реализации A1, B1, A2,
A3, B2, C, P1, P2 (см. §6). Формализует, **что именно** утверждает аналитика
build-recorder, **при каких допущениях** и **чего гарантия не покрывает** —
основа для сертификационных ссылок из отчётов и статьи.

## 1. Назначение и область

build-recorder наблюдает сборку на границе системных вызовов (`ptrace`:
`exec*`, `open*`, `openat2`, `link*`, `rename*`, `close`, `clone/fork/vfork`) и
строит граф происхождения: какой процесс что читал, писал, порождал, с
git-blob-хешами содержимого. Дополнительно он фиксирует **собственные слепые
зоны**: процесс, применивший io_uring (`io_uring_setup`/`io_uring_enter`),
помечается предикатом `b:coverage_gap` (P2). Поверх графа
`provenance-verdict.py` выдаёт вердикт для каждого произведённого файла и, при
указании `--payload`, для каждого **поставляемого** файла (P1).

**Цель — по возможности без вмешательства в сборку** дать обоснованное
утверждение: *пакет собран полностью из исходных текстов, и в его выходные
артефакты не инкорпорированы ранее скомпилированные (прекомпилированные)
бинарные файлы.*

Требование «без вмешательства» — конституирующее: любой режим, требующий менять
команду/конфиг сборки или включать диагностические опции компилятора,
**исключён из гарантии** (может существовать лишь как отдельный опциональный
режим, см. §7 и план, направление E).

## 2. Формулировка гарантии (условно-негативная)

Наблюдение на границе ядра **не** даёт абсолютного доказательства. Точное
утверждение:

> Каждый файл в поставляемом payload имеет провенанс-цепочку, наблюдённую на
> syscall-границе, которая упирается только в (а) исходные тексты и (б) файлы,
> предоставленные доверенным тулчейном / OS-пакетами; и ни один поставляемый
> файл не является и не инкорпорирует ранее существовавший бинарник, вошедший в
> сборку без такой цепочки — **при выполнении допущений T1…T5 (§4)**.

Это не «доказали, что всё из исходников», а «не нашли ни одного выхода **без**
исходной родословной». GREY (§3) — честное «инструмент не может утверждать»,
что для сертификации ценнее ложного GREEN.

**По какому множеству берётся «каждый файл» (P1).** Без `--payload` квантор
пробегает по файлам, которые *попали в граф*, а не по тем, которые *уезжают в
пакет*: файл, записанный ненаблюдённым каналом, не становится GREY, он просто
отсутствует, и его молчание читается как «замечаний нет». Это делало GREEN
вакуумным. С `--payload <buildroot|список путей>` каждый поставляемый файл
сопоставляется с графом **по хешу содержимого** (сопоставление не зависит от
путей: распакованный пакет или перенесённый buildroot сходятся так же), и
несопоставленный файл даёт GREY. Гарантия действительна только в форме
«с `--payload`».

## 3. Вердикт-модель (реализация: `provenance-verdict.py`)

Для каждого произведённого файла прослеживается содержимое к входным листьям
через рёбра `writes` и copy-эджи `hardlink`/`rename`:

| Вердикт | Определение | Exit |
|---------|-------------|------|
| 🟢 **GREEN** | родословная упирается только в исходный текст и файлы OS-пакетов (тулчейн/система) | 0 |
| 🔴 **RED** | инкорпорирует **чужой прекомпилят** — `.o`/`.a`/`.so`/blob, не собранный из исходников в этой сборке и не предоставленный OS-пакетом; слинкованный **или** скопированный/hardlink'нутый прямо в выход | 1 |
| ⚪ **GREY** | произведён без наблюдаемой исходной родословной (сокет/скрытый канал/пробел покрытия) | 3 |

**Вердикт пакета = GREEN ⟺ ноль RED и ноль GREY.**

Формально «чужой прекомпилят» (лист `L`): `L` не произведён в этой сборке ∧
`is_binary(L)` ∧ у `L` нет OS-пакета (по sidecar от `brec enrich` или live-backend).
Исходные листья (`is_binary=false`) допустимы — это и есть «из исходников»;
системные бинарники (есть пакет) допустимы по T1.

## 4. Граница доверия — допущения T1…T5

Гарантия держится ровно на этих допущениях; они **документируются, а не
«чинятся»** наблюдением.

### T1 — Доверие к тулчейну (Trusting Trust)
`gcc`/`as`/`ld` и системные библиотеки сами — прекомпилированные бинарники.
Гарантия всегда «с точностью до доверенного тулчейна»; сборки «только из текста»
без доверенных инструментов не существует (bootstrap).
*Митигация:* тулчейн опознаётся по принадлежности OS-пакету (RPM-атрибуция);
целостность самого тулчейна — вне области build-recorder (отдельная задача:
доверенная база образа, reproducible toolchain).

### T2 — Полнота перехвата syscalls
Гарантия дырява настолько, насколько существуют непокрытые пути входа
содержимого файла. **Статус после A1/A2/A3/B2 — см. §5; критические пути
закрыты.** Остаточные пробелы: символические ссылки (создание не трассируется),
fd, унаследованные/открытые **до** старта трассировки (S3), экзотические
kernel-copy без открытого fd.

**io_uring (P2).** Отдельный класс: операции `IORING_OP_OPENAT`/`READ`/`WRITE`/
`LINKAT` выполняются через кольцо, а в режиме SQPOLL их выполняет ядерный поток
вообще без системного вызова. ptrace не видит ни open, ни write: проверено
экспериментально (файл 43 байта создан и заполнен через кольцо, узла в графе
нет, путь виден лишь как строка в `b:cmd`). Наблюдением это не закрывается
(нужен другой backend захвата, eBPF: X.1, либо запрет io_uring через seccomp,
что является вмешательством). Поэтому пробел не «чинится», а **объявляется**:
трассировщик пишет `b:coverage_gap "io_uring"` на процесс, вердикт при наличии
такой метки не может быть GREEN, а выходы этого процесса помечаются GREY
(наблюдённая родословная не доказана полной).

### T3 — Скрытые каналы содержимого
Байты, эмитированные из встроенного в сам процесс блоба, из сокета, из пайпа,
или записанные в чужую память (`process_vm_writev`, ptrace-инъекция) — файловый
слой их происхождение не видит.
*Детектирование:* такой выход всплывает как **GREY** (запись без исходной
родословной), но не опровергается позитивно.

### T4 — In-process компиляция (JVM/.NET)
`javac` и Roslyn компилируют **внутри** долгоживущего процесса; read-set и
write-set схлопываются, syscall-наблюдение рёбер source→artifact не даёт. Под
запретом на вмешательство — **вне области**; такие выходы должны трактоваться как
**GREY**, а покрытие возможно лишь опциональным интрузивным режимом (план E).

### T5 — Трансформации, скрывающие происхождение
`objcopy`/распаковка/дешифровка прослеживаются, пока каждый шаг — файловая
операция; требуется доверие, что шаг не впрыснул ненаблюдённые байты (иначе — T3).

### Криптографическая стойкость (T-hash)
Хеши содержимого — git-blob. Коллизии **SHA-1** практичны → в состязательной
модели злоумышленник мог бы подогнать прекомпилят под хеш исходно-производного
файла. *Статус:* ✅ реализовано (A4 `1ce9db9`) — опция `-2`/`--sha256` пишет
git-blob **SHA-256** (стойкий к коллизиям). Дефолт остаётся SHA-1 ради
git/RPM-совместимости; **для состязательной строгости трассировать с `-2`**
(вердикт C от алгоритма хеша не зависит и совместим с обоими).

## 5. Покрытие: закрытые и открытые пути (T2)

Пути, которыми содержимое может войти в выход, и их статус (аудит покрытия →
реализация):

| Путь | Syscalls | Статус | Реализация |
|------|----------|--------|------------|
| read→write (компиляция, `cp`, `ld`) | `open`/`openat`/`creat`+`close` | ✅ покрыт (исходно) | — |
| перемещение | `rename*` | ✅ узлы+хеш (исходно) | — |
| **hardlink** | `link`/`linkat` | ✅ **закрыт** | A1 `7e44643` |
| **openat2** | `openat2` | ✅ **закрыт** | A2 `dab43d4` |
| запись без `close` до выхода | — | ✅ **дохеш при reap** | A3 `afcfb4b` |
| гибель процесса по сигналу | `WIFSIGNALED` | ✅ **reap+хеш** | B2 `afcfb4b` |
| обрыв графа при падении трассировщика | teardown | ✅ **флаш Turtle** | B2 `afcfb4b` |
| нерезолвимый путь рвал трассировку | — | ✅ **skip, не abort** | B1 `a939db5` (#226) |
| reflink CoW-копия | `ioctl(FICLONE)` | ✅ покрыт косвенно (оба open видны) | — |
| checked-in прекомпилят через `cp` | `open(RDONLY)` | ✅ виден → RED в C | C `abc7583` |
| сеть → файл | сокет | ⚠️ → **GREY** (T3) | C `abc7583` |
| **io_uring** | `io_uring_setup`/`enter` | ⚠️ **не покрыт, но объявлен** → GREY | P2 |
| **файл в payload без узла в графе** | — | ✅ **ловится сверкой payload** → GREY | P1 |
| символическая ссылка | `symlink*` | 🟠 создание не трассируется | открыт (low) |
| унаследованный/пред-открытый fd | — | 🟠 open мог быть пропущен | открыт (S3) |
| in-process JVM/.NET | — | ⚪ вне области (T4) | план E |

P1 работает как **замыкающая проверка** для всей таблицы: чем бы содержимое ни
вошло в поставляемый файл (io_uring, сокет, непротрассированный процесс,
symlink-манёвр), файл без сопоставления с графом по хешу даёт GREY. Это не
заменяет перехват (не говорит, *откуда* байты), но лишает любую дыру свойства
«молча проходит как GREEN».

## 7. Операционные требования

Гарантия действительна только при соблюдении:

1. **Обогащение.** Прогнать `brec enrich <out> <rpm-dump>` до вердикта (либо
   передать `--rpm-dump`): иначе системные библиотеки без OS-атрибуции ложно
   попадают в RED (T1 не может быть применён). Без дампа live-бэкенды не
   поднимаются: `detect_backends(None)` возвращает пустой список.
   Атрибуция ложится в `<out>.provenance.json` рядом с трассой, а не в саму
   трассу: файл, записанный трассировщиком, остаётся доказательством и после
   обогащения, и его хеш можно предъявить. Sidecar, собранный по другой трассе,
   не применяется молча: записи сверяются с узлами по пути, о расхождении
   команда предупреждает.
2. **Сверка payload (P1).** Запускать вердикт с `--payload`, указывая то, что
   реально уезжает: buildroot, распакованный пакет или список путей
   (`rpm -qpl`). Без него вердикт говорит только о наблюдённых файлах, и
   утверждение о пакете не следует из отчёта:
   ```
   python3 provenance-verdict.py build.out --rpm-dump rpm-dump.txt \
       --payload ~/RPM/BUILDROOT/pkg-1.0-alt1.x86_64
   ```
   Список путей (без содержимого) даёт ослабленную проверку: сверка только по
   пути, о чём отчёт сообщает отдельной строкой `checked by path only`.
3. **Без вмешательства.** Сборка трассируется как есть; никаких диагностических
   флагов компилятора, меняющих поведение (иначе результат вне гарантии).
4. **Доверенная база образа** (T1): тулчейн и системные пакеты из проверенного
   источника; их целостность — предусловие, не результат.
5. **Трактовка вердикта:** GREEN: принять; RED: прекомпилят инкорпорирован
   (разбор обязателен); GREY: инструмент не может утверждать (ручная проверка
   либо признание вне области, напр. T4). Отдельный случай GREY: разрыв
   покрытия (`coverage_gap`): здесь под вопросом не конкретный файл, а полнота
   всего файлового слоя трассы.

## 8. Валидация

- Замкнутость файлового слоя и вердикт проверены end-to-end: обогащённая чистая
  компиляция → GREEN; прекомпилят, hardlink'нутый в дерево сборки (через A1),
  → RED с именем виновного бинарника; синтетика (vendored `.a` + hardlink `.so`
  + blob без родословной) → RED+RED+GREY.
- Робастность: `cat /proc/self/ns/user` (ранее #226-abort) → трасса до конца;
  запись без `close` и запись процессом, убитым SIGSEGV, → верный хеш;
  `SIGTERM` живому трассировщику → валидный Turtle без обрыва.
- **P1+P2 end-to-end (ALT p11, ядро 6.12):** программа на сырых io_uring-syscalls
  (без liburing) создаёт файл через `IORING_OP_OPENAT`+`WRITE`+`CLOSE` и второй
  файл обычным `write`. Результат: `hidden.bin` (43 байта) на диске **узла в
  графе не имеет**, `plain.txt` имеет; трасса несёт `:p0 b:coverage_gap
  "io_uring"`. Тот же `.out` с обогащением:
  - прежняя логика вердикта → 🟢 **GREEN, exit 0** (дыра проходит молча);
  - текущая → ⚪ **GREY, exit 3**: назван разрыв покрытия, `plain.txt`
    понижен до GREY (писал процесс с кольцом), `hidden.bin` пойман сверкой
    payload как «shipped without being observed».
- Тесты: 321 существующий + 16 (`tests/test_provenance_verdict.py`: разрывы
  покрытия, сверка payload по хешу/пути, перенос buildroot, symlink'и,
  подмена содержимого после последней наблюдённой записи): все зелёные.

## 9. Остаточный риск (резюме)

Гарантия **строга против случайного/непреднамеренного** попадания прекомпилята
(через `cp`/`mv`/`ln`/`openat2`/линковку — всё наблюдаемо, §5) при обогащённом
графе. Она **не** абсолютна против:
- целенаправленной подмены по коллизии SHA-1 при трассировке дефолтным
  алгоритмом (T-hash) — устраняется запуском с `-2` (git-blob SHA-256);
- скрытых каналов содержимого (T3): сокет/встроенный блоб → детектируется лишь
  как GREY;
- in-process компиляции JVM/.NET (T4) → GREY, вне области;
- скомпрометированного тулчейна (T1) → предусловие доверия;
- остаточных пробелов T2 (symlink-создание, пред-открытые fd);
- io_uring (P2): не покрыт, объявляется как разрыв → GREY. Ограничение детекта:
  ловится успешный `io_uring_setup`/`io_uring_enter` у трассируемого процесса;
  процесс, получивший готовое кольцо и работающий в режиме SQPOLL без единого
  `enter`, остаётся невидим и ловится только сверкой payload (P1).

Честная граница: **«ноль RED и ноль GREY при допущениях T1–T5, с обогащением и
с `--payload`»**, а не «доказано, что всё из исходников».
