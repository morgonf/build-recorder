# Фаза 0 — тикеты для реализации (Sonnet)

> Родительский документ: `doc/architecture-universal-provenance.md` (§11, фаза 0).
> Цель фазы: ввести общий слой `brec/` (IR + единый парсер `.out`) и перевести
> на него существующие скрипты **без изменения их наблюдаемого поведения**
> (behavior-preserving рефакторинг). Это убирает дублирование парсинга Turtle,
> на котором сейчас держатся два независимых анализатора.
>
> **Порядок выполнения строгий:** T0.0 → T0.1 → T0.2 → T0.3 → T0.4.
> Каждый тикет завершается зелёными тестами и не ломает существующие команды.
>
> **Общие правила для исполнителя:**
> - Python 3.11+, тип-аннотации как в текущих скриптах.
> - Не добавлять тяжёлых зависимостей. Парсер — ручной (как в `enrich.py`/
>   `verify-build.py`), без `rdflib`.
> - Перед написанием парсера **изучить реальный формат** `.out`: сгенерировать
>   фикстуру (см. T0.0) и свериться с регулярками в `enrich.py` и
>   `verify-build.py`. Не полагаться на догадки о формате.
> - Каждый PR трогает только свой тикет. Golden-тесты обязательны там, где
>   сказано «побайтово/идентично».

## T0.0 — Каркас пакета `brec/` и тестовые фикстуры

**Зависит от:** —
**Размер:** S

### Контекст
Сейчас всё в плоских скриптах в корне репозитория. Нужен импортируемый пакет и
детерминированные фикстуры, чтобы последующие тикеты были тестируемы офлайн.

### Объём работ
1. Создать пакет:
   ```
   brec/
   ├── __init__.py          # __version__ = "0.0.0"
   tests/
   ├── __init__.py
   ├── conftest.py
   └── fixtures/
       ├── tiny.out         # см. ниже
       ├── tiny.expected.json
       └── README.md        # как сгенерированы фикстуры
   ```
2. Сгенерировать **маленькую реальную** `.out`-фикстуру `tests/fixtures/tiny.out`:
   собрать build-recorder'ом один из примеров из `examples/` (напр. `f1.c`),
   командой вида `build-recorder -o tiny.out cc -o /tmp/f1 examples/f1.c`.
   Зафиксировать в `fixtures/README.md` точную команду и окружение.
3. Если собрать build-recorder в среде нельзя — **создать `tiny.out` вручную**
   по образцу из `doc/output.md` (минимум: 2 процесса, 3 файла, связи
   `execs/reads/writes/executable`), и пометить в README, что фикстура
   синтетическая.
4. Настроить pytest: `pytest tests/` запускается из корня репозитория.

### Вне объёма
Любой функциональный код в `brec/` (только `__init__.py`).

### Критерий приёмки
- `python -c "import brec; print(brec.__version__)"` работает.
- `pytest tests/` проходит (хотя бы один тривиальный тест-заглушка).
- `tests/fixtures/tiny.out` существует и валиден как Turtle-подобный формат
  build-recorder (визуально соответствует `doc/output.md`).
- `fixtures/README.md` описывает происхождение каждой фикстуры.

## T0.1 — Промежуточное представление `brec/ir.py`

**Зависит от:** T0.0
**Размер:** M

### Контекст
Все стадии конвейера обмениваются версионированным IR, сериализуемым в JSON.
Это позволяет запускать и тестировать стадии независимо.

### Объём работ
Реализовать в `brec/ir.py` dataclasses (см. `architecture-universal-provenance.md`
§3.1–§3.2), на этой фазе — только граф и классификация:

```python
@dataclass
class FileNode:
    uri: str
    abspath: str
    name: str
    size: int
    git_blob_sha1: str

@dataclass
class ProcessNode:
    uri: str
    pid: int
    cmd: str
    executable: Optional[str]      # uri FileNode
    start: Optional[str]
    end: Optional[str]
    reads:  list[str]
    writes: list[str]
    execs:  list[str]              # uri ProcessNode
    role: Optional[str] = None

@dataclass
class BuildGraph:
    files: dict[str, FileNode]
    procs: dict[str, ProcessNode]
```

И конверт:

```python
@dataclass
class IRDocument:
    schema_version: int            # = 1
    stage: str                     # "graph" | "classified" | ...
    source_out: str
    payload: dict
```

Требования:
- `to_dict()` / `from_dict()` на каждой структуре; `IRDocument.dump(path)` /
  `IRDocument.load(path)` (JSON, UTF-8, `ensure_ascii=False`, отсортированные
  ключи для стабильного golden-diff).
- `set`-поля (если появятся) сериализуются как отсортированные списки.
- `from_dict` устойчив к отсутствию опциональных полей (forward-compat).
- При несовпадении `schema_version` — понятное исключение `IRVersionError`.

### Вне объёма
Парсинг `.out` (это T0.2). Структуры `Match`/`Vulnerability` (поздние фазы) —
можно объявить заглушками или не добавлять.

### Критерий приёмки
- Round-trip: `from_dict(to_dict(x)) == x` для всех структур (property-тест на
  сгенерированных данных или табличные кейсы).
- `IRDocument.dump`→`load` даёт идентичный объект.
- Повторный `dump` того же объекта даёт **побайтово** идентичный файл
  (детерминизм для golden-тестов).
- Unit-тесты в `tests/test_ir.py`.

## T0.2 — Единый парсер `brec/model.py`

**Зависит от:** T0.1
**Размер:** L (ключевой тикет фазы)

### Контекст
Сейчас `.out` парсят независимо `sbom.py` (`parse_file_records`, ~стр. 227) и
`verify-build.py` (парсер с `COMPILER_NAMES`/`LINKER_NAMES`, props на ~стр. 189).
Нужен **один** парсер → `BuildGraph`.

### Объём работ
`brec/model.py`:
```python
def parse_out(path: Path) -> BuildGraph: ...
```

Парсер обязан корректно читать **оба** формата, которые встречаются в `.out`
(см. регулярки в `enrich.py`): «плоский» (`:f0 b:abspath "..." .`) и
«сгруппированный» (`:f0 a b:file ; \n b:abspath "..." ; ...`).

Предикаты, которые нужно извлечь (имена — из `doc/build-recorder-schema.ttl`):
- Процесс: `a b:process`, `b:pid`, `b:cmd`, `b:start`, `b:end`, `b:executable`,
  `b:execs`/`b:creates` (связь процесс→процесс), `b:reads`, `b:writes`,
  `b:rename`. (`b:env` можно пропустить на этой фазе — не входит в `ProcessNode`.)
- Файл: `a b:file`, `b:abspath`, `b:name`, `b:size`, `b:hash`.

Требования:
- Снятие Turtle-экранирования строк (повторно использовать/портировать
  `escape`/`unescape` логику из существующих скриптов; в `sbom.py` есть
  `_unescape`).
- URI узлов: `:fNN` для файлов, `:pidNN`/иные для процессов — определять тип по
  тройке `a b:file` / `a b:process`, а не по префиксу имени.
- `role` НЕ заполняется здесь (это CLASSIFY/фаза 1) — оставить `None`.
- Производительность: построчно, без загрузки всего в `rdflib`. Должен
  переваривать `.out` в десятки МБ (исходный envoy-build.out был ~1.9 МБ; целевые
  сборки крупнее).
- Идемпотентность: повторный парс того же файла → эквивалентный `BuildGraph`.

### Вне объёма
Классификация, провенанс, идентификация. Только построение графа.

### Критерий приёмки
- На `tests/fixtures/tiny.out`: число `files`/`procs` и все связи совпадают с
  ожидаемым `tiny.expected.json` (golden).
- **Эквивалентность со старыми парсерами:** добавить тест, который сравнивает
  множество `(uri, abspath, git_blob_sha1)` из `parse_out()` с тем, что
  извлекает текущий `sbom.parse_file_records()` на том же `.out` — множества
  идентичны.
- Тест на оба формата Turtle (плоский и сгруппированный) — подготовить по
  фикстуре на каждый.
- Тест на экранированные пути (пробелы, кавычки, юникод в abspath).
- `tests/test_model.py`.

## T0.3 — Перевод `sbom.py` и `verify-build.py` на `brec/model.py`

**Зависит от:** T0.2
**Размер:** L

### Контекст
Убрать собственные парсеры из обоих скриптов, оставив их CLI и вывод **без
изменений** (behavior-preserving).

### Объём работ
1. Перед началом зафиксировать **golden-выводы** на эталонных `.out`:
   - запустить текущие `sbom.py` и `verify-build.py` (со всеми основными
     флагами: `--report`, `--json`, `--upstream-verify` для verify;
     `-o sbom.json`, `--report` для sbom) на доступных фикстурах
     (минимум `tiny.out`; при наличии — civetweb/aria2 `.out`);
   - сохранить результаты в `tests/golden/`.
2. Заменить внутренние парсеры на `brec.model.parse_out()`. Внутренние
   структуры (`FileRecord` в `sbom.py`, узлы в `verify-build.py`) адаптировать
   как тонкие адаптеры над `FileNode`/`ProcessNode` (или заменить напрямую,
   если это не меняет вывод).
3. `role`-логику и классификацию пока **оставить в скриптах как есть** — её
   вынос это фаза 1 (T1.2). Здесь меняется только источник графа.

### Вне объёма
Любые изменения формата вывода, новые флаги, вынос классификации.

### Критерий приёмки
- **Golden-тесты:** вывод `sbom.py` и `verify-build.py` на всех фикстурах
  **побайтово** совпадает с зафиксированным до рефакторинга (с поправкой на
  заведомо недетерминированные поля — timestamp генерации и т.п.; такие поля
  нормализовать в тесте и задокументировать).
- Команды из `doc/sbom-vendored-deps.md` (pipeline) выполняются без ошибок.
- В обоих скриптах больше нет собственного построчного парсера `.out` (grep по
  `re.compile(r"...b:file...")` в них пуст).
- `tests/test_regression_sbom.py`, `tests/test_regression_verify.py`.

## T0.4 — Миграция чтения старых RDF-предикатов

**Зависит от:** T0.2
**Размер:** S

### Контекст
Уже записанные `.out` используют `b:rpm_package`, `b:rpm_name`, `b:dep_type`.
План (§4) вводит обобщённые `b:pkg_backend/pkg_name/pkg_version/purl`. Чтобы
старые файлы продолжали читаться, парсер должен понимать оба набора.

### Объём работ
В `brec/model.py` (или `brec/provenance/compat.py`) добавить чтение-совместимость:
- `b:rpm_name`   → трактовать как `pkg_name` (backend="rpm")
- `b:rpm_package`→ `pkg_version` (NEVRA) (backend="rpm")
- `b:dep_type`   → сохранять как есть в дополнительном поле (понадобится в T1.2
  для маппинга в `DepClass`; на этой фазе — просто не терять значение).
- Если присутствуют новые `b:pkg_*` — они имеют приоритет над `b:rpm_*`.

Реализовать так, чтобы это не зависело от того, есть ли в `.out` enrichment
вообще (неенричнутые файлы парсятся штатно, без пакетных полей).

### Вне объёма
Запись новых предикатов (это enrich-сторона, фаза 1). Сам провенанс-lookup.

### Критерий приёмки
- Фикстура «старый enriched .out» (с `b:rpm_*` и `b:dep_type`) парсится, поля
  доступны через модель.
- Фикстура «новый .out» (с `b:pkg_*`) парсится, новые поля имеют приоритет.
- Фикстура «без enrichment» парсится без ошибок (пакетные поля = None).
- `tests/test_compat.py`.
