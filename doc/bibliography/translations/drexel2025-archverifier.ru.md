## 0. Краткая выжимка (один слайд)

- Статья = **обзор reproducible builds (R-B) за 10 лет** + **собственный вклад**: развёрнут
  независимый верификатор пакетов Arch Linux на `rebuilderd`.
- Найдены и исправлены два реальных бага невоспроизводимости:
  1. **certbot** (16 пакетов) — рассинхрон версии зависимости в SBOM-файле `.BUILDINFO`;
  2. **fwupd** — таймстемп в gzip-заголовке (Python-gzip вместо GNU-gzip).
- Общий тезис: R-B + bootstrappable builds + аудит исходников = связка против supply-chain-атак;
  но на практике даже у Arch воспроизводимо лишь **75,8%** пакетов — путь не пройден.

## 1. Постановка задачи

**Проблема доверия к бинарнику.** Пользователи и компании почти никогда не собирают софт
сами — качают **готовый бинарник**. Доказать, что этот бинарник получен из заявленного,
неизменённого исходника, — трудная задача. Аудит исходного кода не помогает: между
исходником и поставляемым бинарём нет проверяемой связи.

**Reproducible Builds (R-B)** — решение: дать **независимо проверяемый путь исходник → бинарь**.
Любой, у кого есть исходник + точные инструкции сборки + зависимости, должен получить
**побитово идентичный** артефакт, сколько бы раз и где бы ни собирал.

**Польза R-B (для слайда «зачем»):**
- независимые верификаторы подтверждают, что выложенный бинарь = выложенный исходник;
- детектируются атаки на сборочную инфраструктуру;
- бонусы помимо безопасности: выше cache-hit при сборке → дешевле разработка;
- перспектива: intrusion detection, build-honeypots, требование для сертификации critical-софта.

## 2. Базовые понятия (готовый глоссарий для презентации)

| Термин | Определение |
|--------|-------------|
| **Source code** | человекочитаемые файлы на языке программирования |
| **Build toolchain** | набор инструментов исходник → машинный код: компилятор, ассемблер, линкер, интерпретатор |
| **Artifact** | любой выход тулчейна, кроме plaintext-логов: бинарь, библиотека, tarball, пакет, образ ФС |
| **Reproducible Build (R-B)** | сборка детерминирована: при фиксированных исходнике и зависимостях **каждый** билд даёт **побитово идентичный** артефакт, независимо от окружения |
| **Bootstrappable Build (B-B)** | разрыв цикла «компилятор собирается компилятором»: чёткий путь от минимального аудируемого seed, без слепого доверия большому начальному бинарю |
| **Diverse Double-Compiling (DDC)** | техника Уилера против trusting-trust: проверка соответствия бинаря компилятора его исходнику через независимый второй компилятор |
| **SBOM** | вложенная опись всех компонентов сборки (FOSS, проприетарные, библиотеки, зависимости); в Arch — файл `.BUILDINFO` |

> **Важная оговорка авторов:** R-B **не делает софт безопаснее**. Небезопасный софт останется
> небезопасным. R-B лишь гарантирует, что бинарь соответствует **именно тому** исходнику —
> ни больше, ни меньше.

## 3. История R-B (хронология для слайда-таймлайна)

| Год | Событие |
|-----|---------|
| **1984** | Кен Томпсон, тьюринговская лекция «trusting trust» — посеял интерес к проблеме доверия к бинарям |
| **1990-е** | Cygnus делает GNU-инструменты (gcc, gdb, binutils, make) воспроизводимыми — первый известный случай R-B (раскрыт лишь 25 лет спустя) |
| **2000-е** | обсуждения в рассылке Debian; распространено мнение, что R-B недостижимы |
| **2011** | **Bitcoin Core** делают воспроизводимым (защита от кражи кошельков подменённым бинарём) — доказали выполнимость |
| **2013** | **Tor Browser** вслед за Bitcoin; на DebConf13 Jérémy Bobbio (lunar) запускает публичную дискуссию → выделены 3 главные причины невоспроизводимости (таймстемпы, пути, локали) |
| **2021** | Executive Order США по кибербезопасности — SBOM и R-B названы средством против supply-chain-атак |
| **2023** | Debian 95,2% воспроизводимы (Bookworm/amd64); Arch 75,8%; Qubes OS, Tails присоединяются |

## 4. Анатомия невоспроизводимости (ядро для технического слайда)

Из **422** задокументированных и категоризированных багов (по состоянию на ноябрь 2023):

| Категория | Доля | Примеры |
|-----------|------|---------|
| **Таймстемпы** | 30% | C++-макросы `__DATE__`, gzip-заголовки, man-страницы, PDF из LaTeX, Doxygen, Maven-version-файлы |
| **Рандомизация** | 17% | случайный порядок файлов в tarball, случайные хеши в Cython, порядок в статических библиотеках, fat-LTO-объекты |
| **Пути** | 16% | build-путь, зашитый gcc/Rust; абсолютные пути в CMake-файлах от Meson |

**Типовые лекарства:** спецификация `SOURCE_DATE_EPOCH` (фиксированное «время сборки»),
относительные пути в gcc вместо абсолютных, детерминированная сортировка в архиваторах.

**Ключевой инструмент диагностики — `diffoscope`:** берёт два несовпавших артефакта,
рекурсивно распаковывает (архивы, образы) и дизассемблирует, выдаёт **читаемый diff**
с подсветкой таймстемпов/путей. Помогает и со сложными случаями (embedded-рандом,
неинициализированная память, ASLR). Несмотря на прогресс автоматизации — R-B остаётся
**ручным и трудоёмким** процессом.

## 5. Открытые проблемы (слайд «почему путь не пройден»)

1. **Осведомлённость.** R-B/B-B по-прежнему неизвестны многим разработчикам; неосознанно
   вносится новый недетерминизм.
2. **Политика.** Достичь 100% можно лишь решением **не паковать** невоспроизводимый софт —
   решение спорное, может вызвать форки.
3. **Инфраструктура архивов.** Для тестирования нужны старые версии зависимостей. Debian
   Snapshot хранит пакеты с 2005 г.; Arch Archive — лишь несколько лет (старое уходит в
   Internet Archive). Дорого, малым проектам не по карману.
4. **Независимые ребилдеры.** R-B полезны только при наличии независимых верификаторов,
   непрерывно пересобирающих софт. Их **мало** — это и есть мотивация статьи.

## 6. Вклад статьи (главная часть)

### 6.1. Независимый верификатор Arch на `rebuilderd`

Развёрнут сервер `rebuilderd` (автор — kpcyrd), статус публикуется на
`reproducible.crypto-lab.ch`.

**Почему Arch:** (1) минимальные дистро-специфичные изменения относительно upstream;
(2) описания сборки `PKGBUILD` — это bash-скрипты, читаемые даже без опыта пакетирования.

**Как работает (схема для слайда):**

```
   Arch mirror
       │  sync-демон: проверка/скачивание новых пакетов каждые 5 минут
       ▼
   rebuilderd ──► worker#0 ... worker#n   (динамически по нагрузке)
       │              собирают пакет ЗАНОВО из исходника
       ▼
   побитовое сравнение с официальным бинарём  →  статус:
       ├─ GOOD   — воспроизводим
       ├─ BAD    — не собрался / не воспроизводим
       └─ UNKWN  — ещё не проверен
       ▼
   NGINX: веб-страница со статусом, build-логами,
          diffoscope-логами (для BAD), attestation-логами (для GOOD)
```

**Железо (полезно для «стоимости»):** сам `rebuilderd` неприхотлив (1 vCPU, 1 ГБ RAM).
Воркеру нужно **≥32 ГБ RAM** на все пакеты; **≥64 ГБ + tmpfs** на крупные (ядро, браузеры).
Начальная установка — 2 VM по 16 vCPU / 64 ГБ / 200 ГБ SSD.

**Тонкость очереди:** GOOD-пакеты не перепроверяются до новой версии. BAD ставятся в очередь
бесконечно (с задержкой). Базовую задержку увеличили с 24 ч до 1 недели, чтобы
невоспроизводимые пакеты не тормозили проверку новых версий.

### 6.2. ПРИМЕР 1 — баг certbot (16 пакетов) ★ ключевой для нас

**Контекст.** Certbot — официальный инструмент получения TLS-сертификатов Let's Encrypt,
критический софт (миллионы пользователей; зловредная версия → утечка приватных ключей).
В Debian certbot-пакеты воспроизводимы — значит технических причин невоспроизводимости в
Arch нет.

**Механизм Arch-сборки (нужен для понимания бага):**
- `PKGBUILD` — bash-скрипт сборки; переменные `depends`/`makedepends`/`checkdepends`
  задают зависимости, которые **скачиваются и устанавливаются ДО** запуска любых функций.
- Минимум — функция `package()`; опционально `prepare()`, `pkgver()`, `build()`, `check()`.
- `pkgver()` — обновляет переменную `pkgver` (версию пакета). В данном случае брала
  фиксированный git-commit → определяла tag → писала в `pkgver`.
- `.BUILDINFO` — SBOM-файл **внутри** пакета: какие версии зависимостей реально стояли.

**Корень бага (суть в одной фразе):**

> `pkgver()` меняет описание сборки **после** того, как зависимости уже скачаны и установлены.
> Переменная `pkgver` ранее использовалась для определения версии зависимости `python-acme`.
> В `.BUILDINFO` записывается одна версия `python-acme`, а PKGBUILD-скрипт требует другую —
> **рассинхрон между задекларированным в SBOM и фактически использованным**.

```
PKGBUILD: установить зависимости (в т.ч. python-acme=ВЕРСИЯ_1)
          ↓
          pkgver() меняет pkgver  ──►  теперь PKGBUILD «требует» python-acme=ВЕРСИЯ_2
          ↓
.BUILDINFO (SBOM) фиксирует:  python-acme = ВЕРСИЯ_1  (то, что реально стояло)
          ↓
рассинхрон: SBOM ≠ требование скрипта  →  пересборка невозможна  →  BAD
```

**Предложенный фикс:** пропатчить тулчейн Arch, чтобы он **падал**, если функция меняет
build-описание (PKGBUILD) **после** установки зависимостей.

### 6.3. ПРИМЕР 2 — баг fwupd (исправление в исходнике upstream)

**Контекст.** fwupd — стандартный инструмент обновления прошивок устройств в Linux
(прямое отношение к безопасности supply chain). Чинить в upstream лучше, чем в дистрибутиве:
исправление чинит пакет **во всех** дистрибутивах сразу.

**Корень:** классический embedded-таймстемп в **заголовке gzip-файла**.

**Почему не поймали раньше (поучительная деталь):** файл сжимался **Python-скриптом**
через `gzip` из стандартной библиотеки Python, а **не** стандартным GNU-инструментом `gzip`.
Привычные средства/практики смотрят на GNU-gzip — питоновский проскользнул мимо.

**Исход:** отправлен upstream-патч, быстро принят. Делает fwupd воспроизводимым в Arch и
в любом дистрибутиве, как только выйдет релиз.

## 7. Выводы статьи

- R-B — **единственный** способ валидировать SBOM через независимую проверку.
- B-B — окончательная защита от trusting-trust на этапе сборки.
- Связка B-B + R-B + регулярный аудит исходников = однозначная привязка исходник↔бинарь
  и реальное снижение supply-chain-рисков.
- Открытые проблемы: нужна **сеть** независимых ребилдеров; софт самих верификаторов тоже
  должен быть воспроизводим (пока не так); множество частных багов ещё не исправлено.

## 8. Что из этого брать в нашу статью (для нас, build-recorder)

### Контраст (главная ось)

| | **Эта школа (R-B / rebuild-and-compare)** | **build-recorder (наш подход)** |
|---|---|---|
| Метод | пересобрать заново + побитово сравнить | трассировать **единственную** фактическую сборку |
| Нужна вторая сборка? | **да** (и сеть независимых верификаторов) | **нет** |
| Взгляд на шаг сборки | **чёрный ящик** (сравниваются только выходы) | **внутрь шага**: какие байты/файлы реально вошли (syscall-трассировка) |
| Что доказывает | «бинарь детерминированно повторяем» | «вот этот блоб ← вот этот git-объект» (атрибуция) |
| Слабое место | не ловит trusting-trust (нужен DDC); требует ресурсов и инфраструктуры архивов | доверяет компилятору как чёрному ящику (тоже не ловит Томпсона) |

### Готовый пример для введения ★

**Certbot-кейс — живая иллюстрация тезиса «декларативный SBOM врёт, фактическая трассировка — нет».**
`.BUILDINFO` (SBOM) зафиксировал версию `python-acme`, **отличную от реально использованной**.
build-recorder записал бы **фактический** вход сборки — такой рассинхрон у нас невозможен по
построению. Это сильнее абстрактного «SBOM-генераторы согласуются на 8–13%» (`ozkan2024-*`,
ARES-2024): здесь конкретный critical-софт, конкретный механизм, реальный баг-репорт.

### Числа, которые можно цитировать

- Воспроизводимость на практике: Arch **75,8%**, Debian 95,2% (ноябрь 2023) — даже лидеры
  не на 100% → усиливает контраст с `lamb2021-reproducible` («воспроизводимость трудна»).
- Причины невоспроизводимости: таймстемпы 30% / рандом 17% / пути 16% из 422 багов.

### Граница нашего метода (честно отграничить перед рецензентом)

trusting-trust (Томпсон) — **ортогональная** проблема, решается DDC/bootstrappable builds.
build-recorder отвечает на вопрос «**чьи байты вошли**», а не «честен ли компилятор».
Мы доверяем компилятору как чёрному ящику и заражённый по Томпсону gcc не поймаем — и не
претендуем; у этого свой инструмент (DDC). Это нужно явно проговорить, чтобы снять
очевидное возражение.

## Приложение: связанные термины (для Q&A на защите)

- **trusting trust** (Томпсон, 1984): компилятор с двойной закладкой — заражает изделия и
  самовоспроизводит закладку при своей пересборке; исходник при этом чист. Аудит кода
  бессилен. R-B **не ловит** (все собирают одинаковый заражённый бинарь → «GOOD»).
- **DDC** (Diverse Double-Compiling, Wheeler 2005/2010): `X = compile(sₐ, B)`;
  `Y = compile(sₐ, X)`; проверка `Y == A`. Ловит несоответствие бинаря компилятора `A`
  его исходнику `sₐ` через независимый компилятор `B`. Стоит на плечах R-B (нужна
  побитовая воспроизводимость).
- **bootstrappable builds**: построение тулчейна от крошечного аудируемого seed
  (напр. `live-bootstrap`, `mes`), чтобы вообще не доверять большому начальному бинарю.
  DDC — детективный (проверить данный бинарь), B-B — профилактический (устранить
  необходимость доверия). Дополняют друг друга.
