## Структура обзора (5 разделов)

### 1. Задача и зачем она нам
- Атрибуция unbuilt-блоба: для бинарника, не собранного из наблюдаемых исходников, —
  чей он и какой версии. Два уровня: **что собрано** (проект/версия) и **чем собрано**
  (компилятор/опции).
- Связь с verify-build: build-recorder ловит «не из исходников собранный» блоб; эти работы —
  кандидат на «второй уровень» (идентификация происхождения).
- *Тезис:* мы и так обязаны защищать сравнение с этим классом перед рецензентом → обзор
  делается один раз и капитально.

### 2. Эволюция признаков (хребет нарратива)
```
ТЕКСТ            СТРУКТУРА              ВЕРСИЯ                СЕМАНТИКА
строки/символы → +control-flow+веса → +function-level/    → эмбеддинги
(OSSPolice'17)   (B2SFinder'19)        two-stage             функций
                                       (B2SMatcher'21)       (BinaryAI'24)
                            ⊥ вендоринг/модификация (CENTRIS'21)
```
- Каждый шаг — ответ на **провал предыдущего**: строки не совпадают (Foxit/OpenSSL:
  19,7% строк) → control-flow; control-flow не различает версии (FP) → function-level;
  ручные фичи хрупки к обфускации/инлайну → выученные эмбеддинги.
- Под-ветка тулчейна повторяет ту же дугу: idioms+CRF (Rosenblum'11) → BERT по байтам
  (BinProv'22) = «ручные признаки → выученные представления».

### 3. Сравнительная таблица + разбор осей
- (таблицы выше) + текст: гранулярность, что каждый НЕ видит, цена (время/обфускация-стойкость).
- Отдельно: коммерческие/проприетарные (BinaryAI, Cybellum) vs открытые.

### 4. Под-ветка тулчейна
- «Чем собрано» — ортогонально «что собрано». Для unbuilt-блоба: не только «чужой», но и
  «собран gcc-X с -O2». Наш `readelf -p .comment` (SAFEC) — тривиальный частный случай.
- Rosenblum (дизасм+idioms+CRF) → BinProv (байты+BERT, без дизасма).

### 5. Общий разрыв всего класса = наша ниша ★
- **Главный тезис обзора.** У ВСЕХ работ один слепой угол:
  1. работают **постфактум по финальному бинарю**;
  2. дают **вероятностную** оценку (сходство/классификация), не точную привязку;
  3. **реконструируют вход сборки** — B2SMatcher даже ML-ом угадывает, какие исходные
     файлы компилировались (partial build, zlib 7,3%); они **сами** называют хукинг сборки
     точным путём (Duan 2019), но отвергают — для COTS сборка недоступна.
- build-recorder **наблюдает** фактическую сборку: точный список вошедших файлов и точную
  команду компилятора (версия+флаги) как **ground truth** там, где весь класс — оценивает.
- Контраст бьёт **не в отдельную статью, а в весь класс**: «угадывание по артефакту vs
  наблюдение процесса». Это сильная позиция перед рецензентом.
- Честная граница: класс решает задачу, которой у нас нет (COTS без исходников/сборки);
  мы — задачу провенанса при доступной сборке. Оси дополняют друг друга, но для verify-build
  именно наблюдение даёт точность, недостижимую для post-hoc-сходства.
