## Аннотация

Сторонние библиотеки (third-party libraries, TPL) активно переиспользуются для повышения
продуктивности разработки, но вносят риски безопасности — например, распространение
уязвимостей. Анализ состава ПО (software composition analysis, SCA), выявляющий
переиспользованные TPL, стал обязательной процедурой современного DevSecOps. Один из
основных подклассов SCA — **binary-to-source SCA**: идентификация исходных проектов,
содержащихся в бинарном файле, через сопоставление бинарного и исходного кода. Это серьёзный
вызов реверс-инжиниринга, поскольку после компиляции бинарный и исходный код существенно
расходятся. Существующие техники binary-to-source SCA опираются на базовые синтаксические
признаки (строковые литералы и т. п.), которые избыточны на крупных датасетах TPL и
неустойчивы, что ведёт к ложным срабатываниям и снижению полноты.

Мы предлагаем **BinaryAI** — новую технику binary-to-source SCA с двухфазным сопоставлением,
улавливающим как синтаксические, так и семантические признаки кода. Сначала BinaryAI обучает
модель на базе трансформера, порождающую эмбеддинги уровня функции и извлекающую похожие
исходные функции для каждой бинарной. Затем, применяя **локальность времени компоновки**
(link-time locality), BinaryAI обнаруживает переиспользованные TPL по доле совпавших исходных
функций. Эмбеддинг-модель BinaryAI превосходит SOTA-модель CodeCMR (recall@1 22,54 % против
10,75 %, MRR 0,34 против 0,17). В задаче обнаружения TPL BinaryAI обходит все существующие
инструменты binary-to-source SCA, повышая точность с 73,36 % до 85,84 % и полноту с 59,81 %
до 64,98 % относительно признанного коммерческого SCA-продукта.

## 1. Введение

SCA выявляет open-source-компоненты (переиспользованные TPL) внутри артефактов ПО, позволяя
отслеживать привнесённые ими угрозы — распространение уязвимостей, нарушение лицензий.
Из-за рисков доступа к исходному коду (privacy policy и пр.) преобладающей стала бинарная
SCA, легко встраиваемая в фазу сборки или развёртывания DevSecOps-конвейера. По форме TPL в
базе бинарная SCA делится на **binary-to-binary** и **binary-to-source**.

Существующие binary-to-source-техники используют базовые синтаксические признаки (например,
строковые литералы), сохраняющиеся после компиляции. Эталон — **B2SFinder**, применяющий
взвешенный алгоритм сопоставления трёх типов таких признаков. У подхода два ограничения:

1. **Избыточность** базовых признаков на крупном датасете TPL — один и тот же признак
   дублируется во множестве библиотек, снижая уникальность и порождая ложные срабатывания
   (падение точности).
2. **Малое число общих признаков** между переиспользованной TPL и целевым бинарником,
   особенно когда бинарник *stripped* (удалены имена функций и часть строк), — падает полнота.

Бинарный код сильно отличается от исходного, и мало признаков остаётся неизменным после
компиляции. Поэтому нужны более гранулярные признаки **уровня функции**, несущие больше
высокоуровневой синтаксической и семантической информации.

**Наш подход.** Учитывая расхождения, вносимые компиляцией, BinaryAI применяет модель на базе
трансформера для захвата токен-ориентированных синтаксических признаков и порождения
эмбеддингов функций. Базовая модель — большая языковая модель **Pythia**, дообученная в
режиме supervised contrastive learning. Эмбеддинги всех исходных функций крупного датасета TPL
вычисляются офлайн и хранятся в векторной БД (корпусе). При онлайн-анализе целевого бинарника
BinaryAI декомпилирует его, кодирует бинарные функции в эмбеддинги-запросы и извлекает top-k
похожих исходных функций. Затем во второй фазе применяется **сопоставление по локальности**:
link-time locality и граф вызовов как структурная семантика позволяют выбрать точно совпавшую
исходную функцию из top-k. По доле общих функций сверх порога BinaryAI идентифицирует
переиспользованную TPL и её потенциальные угрозы.

**Вклад статьи:**

- Впервые применено сопоставление бинарного и исходного кода **на уровне функций** к задаче
  binary-to-source SCA; обучена трансформер-модель для извлечения похожих исходных функций.
- Предложено **двухфазное** сопоставление с использованием link-time locality для повышения
  точности подбора функций из top-k.
- Экспериментально показано, что модель BinaryAI значительно превосходит CodeCMR, а сам
  BinaryAI доминирует среди существующих инструментов binary-to-source SCA.

## 2. Предпосылки и мотивация

### 2.1. Анализ состава ПО

SCA выявляет TPL в целевом проекте для отслеживания угроз и нарушений лицензий. Бинарная SCA
извлекает признаки из крупного датасета TPL, строит базу и через детектирование клонов кода
находит схожие признаки; TPL признаётся переиспользованной, если число совпадений превышает
порог.

**2.1.1. Binary-to-source SCA.** Датасет — масштабно собранные open-source C/C++-проекты
(в основном GitHub и пакеты GNU/Linux). Сопоставляя признаки исходного кода с бинарником,
техника находит переиспользованные TPL на уровне исходников. Фундаментальный шаг —
*сопоставление бинарного и исходного кода* (binary source code matching). Эталон B2SFinder
выбирает базовые синтаксические признаки, устойчивые к компиляции. Эффективность таких техник
в целом страдает из-за существенных расхождений между бинарным и исходным кодом.

**2.1.2. Binary-to-binary SCA.** TPL хранятся в бинарном виде, собранном из исходных пакетов
(через пакетные менеджеры, например Nix, — для разных версий, архитектур, уровней оптимизации).
Современные техники (ModX и др.) применяют эмбеддинг-подходы для детектирования сходства между
бинарниками, захватывая в т. ч. семантику (граф потока управления, CFG).

### 2.2. Мотивация

**Слабость binary-to-binary SCA — плохая масштабируемость датасета.** Из-за сложности
автоматической компиляции лишь малая часть пакетов собирается в множество бинарных версий.
Пример: ModX берёт 100 наиболее частых TPL из 795, поддерживаемых Nix, тогда как крупнейший
датасет для binary-to-source SCA содержит ~10 тыс. TPL (×100). Малый масштаб датасета резко
снижает практичность SCA. Поэтому основным объектом исследования выбран **binary-to-source SCA**.

**Слабости binary-to-source SCA.** Базовые признаки (строковые литералы):
- сильно **избыточны** — строка «407 Proxy Authentication Required» встречается в >50 TPL
  собранного датасета; избыточность снижает уникальность и порождает ложные срабатывания;
- часто **отсутствуют** общими между TPL и целевым бинарником, особенно для stripped-файлов;
  к тому же извлечение строк из C/C++ неустойчиво (теряются строки, склеенные из макросов и
  констант), что снижает полноту.

Вывод: нужны гранулярные признаки уровня функции, обрабатывающие высокоуровневую семантику.
Учитывая расхождения бинарных и исходных функций после компиляции, BinaryAI улучшает
binary-to-source SCA трансформер-моделью, порождающей эмбеддинги уровня функции.

## 3. Подход

Рабочий процесс BinaryAI (рис. 1) состоит из четырёх фаз: ❶ извлечение признаков (3.1),
❷ поиск функций по эмбеддингам (3.2), ❸ сопоставление по локальности (3.3), ❹ обнаружение
TPL (3.4). Важно: сопоставление бинарного и исходного кода — **не end-to-end**, а две
раздельные стадии (❷ синтаксис → ❸ семантика).

### 3.1. Извлечение признаков

**Исходные функции.** Все проекты датасета используют git. Для каждого собираются C/C++-файлы
по всем версиям (git-тегам), файлы различаются по хэшу содержимого. Парсером **tree-sitter**
строится AST, извлекаются все уникальные исходные функции. Ведутся два инвертированных индекса:
функция → файлы, её содержащие; функция → TPL, её содержащие.

**Бинарные функции.** Бинарник анализируется фреймворком **Ghidra** (NSA): дизассемблирование,
выделение функций, декомпиляция в C-подобный псевдокод. Из Ghidra извлекаются относительный
виртуальный адрес (`bin_rva`) как порядковый номер для link-time locality и граф вызовов как
межфункциональная связь. BinaryAI рассчитан на **stripped**-бинарники (без отладочной и
символьной информации) — типичный реальный случай.

### 3.2. Поиск функций по эмбеддингам

Ключевая идея — обучить модель, отображающую бинарные и исходные функции в **единое векторное
пространство**, где похожие пары близки, непохожие — далеки; сходство считается по эмбеддингам.
Обычное обучение представлений работает с одним форматом (source-to-source либо
binary-to-binary); здесь же нужна кросс-форматность. Языковые модели хорошо учат синтаксис
как естественного, так и программных языков, а мультиязычная модель способна узнавать схожие
токен-признаки в разных форматах.

В качестве базовой взята **Pythia** (инициализация — `pythia-410m`, 410 млн параметров;
ранее пробовались OPT и BLOOM, но Pythia дала оптимум). Дообучение — **контрастное** (supervised
contrastive learning) с функцией потерь **CLIP** (изначально для выравнивания изображений и
подписей). Процесс (рис. 2): функции токенизируются, прогоняются через Pythia, эмбеддинг —
выход последнего скрытого слоя; для i-й позитивной пары обозначим (eᵢᵇ, eᵢˢ) эмбеддинги
бинарной и исходной функции; (eᵢᵇ, eⱼᵇ) при i≠j — негативный пример. В батче из N
binary-to-source-пар CLIP строит матрицу косинусных сходств; цель — максимизировать сходство
N позитивных пар и минимизировать для N·(N−1) негативных через симметричную кросс-энтропию.
Итоговая потеря L_CLIP = (L_bin + L_src)/2 (формулы 1–2). Дополнительно применён **MoCo**
(Momentum Contrast) — динамические словари увеличивают число негативов и усиливают обучение.

Развёртывание: офлайн вычисляются эмбеддинги **всех 56 342 179 уникальных исходных функций из
12 013 TPL**, хранятся в векторной БД (корпусе). Онлайн: из целевого бинарника извлекаются
бинарные функции, в реальном времени кодируются в эмбеддинги-запросы, которыми из корпуса
извлекаются top-k похожих исходных функций. Идентификатор бинарной функции — `bin_rva`; к
каждой исходной функции через инвертированный индекс прикрепляются содержащие её файлы. Пример
(рис. 3): для бинарной `FUN_00153d7b` извлечена исходная `DefaultLogDir()` с косинусным
сходством 0,982 (истинно-позитивная пара).

### 3.3. Сопоставление по локальности (locality-driven matching)

Брать просто top-1 по эмбеддингу нельзя: из-за мелких различий между версиями в крупном
датасете много почти одинаковых функций, и одних токен-признаков недостаточно. Вторая фаза
использует **link-time locality** (`bin_rva`) и **граф вызовов** как структурную семантику.

Базовые наблюдения о C/C++-тулчейне (компилятор `file.c` → `obj.o`, компоновщик объединяет
объектные файлы, сливая секции кода):
1. Все функции одного исходного файла компилируются в один объектный файл (хотя их взаимное
   расположение может меняться).
2. Объектные файлы непрерывно компонуются в бинарник; функции внутри секции кода объектного
   файла сохраняют взаимную локальность.
3. Из-за шаблонов C++ и условной компиляции одна исходная функция может соответствовать
   нескольким бинарным («1-к-n»).

Отсюда: бинарные функции из одного исходного файла располагаются в бинарнике **непрерывным
интервалом**. Восстанавливая границы объектных файлов через интервалы непрерывных функций
(reverse engineering), можно определить исходные файлы, попавшие в бинарник, и точнее
сопоставить функции.

**Алгоритм 1.** Для каждой исходной функции из top-k собирается индекс `file2pairs` (файл → все
извлечённые пары бинарная/исходная функция). Результат инициализируется top-1-функцией. Для
каждого файла извлекается непрерывный интервал функций: пары сортируются по `bin_rva`, скользящее
окно с двумя указателями (i, j) нарезает интервал (функция `MaxFileInterval`), удовлетворяющий
двум условиям: число исходных функций в интервале ≤ общего числа функций в файле; интервал
содержит максимум пар. Выбор файлов сводится к **задаче покрытия интервалами** и решается
жадно: интервалы сортируются по приоритету (меньшая начальная точка, бо́льшая конечная, больше
охваченных пар) — предпочтение длинным, покрывающим больше функций; перекрытия исключаются
(начало интервала выше конца предыдущего). Изолированные пары считаются невалидными.

Поскольку внутри файла возможны связи «1-к-n» и «n-к-n» (похожие функции), даже верный файл не
гарантирует верного подбора функций. Для уточнения применяется **граф вызовов**
(`RestrictByFCG`): если для двух пар (bin₁,src₁) и (bin₂,src₂) есть вызовы и между бинарными, и
между исходными функциями (bin₁→bin₂ и src₁→src₂), обе пары считаются верными, а отображения
этих бинарных функций в другие исходные — отфильтровываются. Пример (рис. 4): в интервале
[25697, 287b3] бинарная `FUN_00028061` и исходная `cJSON_AddTrueToObject` имеют по два вызываемых
объекта, тоже совпавших в файле, — выводятся три верных совпадения.

### 3.4. Обнаружение TPL

**Алгоритм 2.** Для каждой совпавшей исходной функции из базы извлекаются все содержащие её TPL.
Так как функции массово клонируются между TPL (internal code clones), наивное удержание всех
TPL даёт ложные срабатывания (пример: бинарник содержит только zlib, но другие TPL,
переиспользующие zlib, тоже опознаются через общие функции). Для фильтрации используется
**зависимость между TPL** (TPL dependency), построенная заранее техникой **TPLite** (на основе
*function birth time* — самого раннего времени релиза — и иерархической информации о путях):
если переиспользуемая TPL пересекается со списком кандидатов, она удаляется (пример: `deflateInit`
есть и в zlib, и в llvm; llvm переиспользует zlib → оставляем zlib). Затем для каждой оставшейся
TPL считается доля совпавших функций к общему числу её исходных функций; при превышении порога θ
TPL признаётся компонентом бинарника. Угрозы безопасности проверяются по официальной базе
уязвимостей (NVD).

## 4. Оценка

Исследовательские вопросы:
- **RQ1:** насколько эффективна эмбеддинг-модель в измерении сходства бинарных и исходных функций?
- **RQ2:** как работает двухфазное сопоставление кода?
- **RQ3:** какова точность обнаружения TPL против SOTA?

### 4.1. Датасеты

- **Обучающий.** Конвейер автокомпиляции на официальных пакетах ArchLinux и AUR (`makepkg`),
  с перехватом компилятора для генерации отладочной информации DWARF. Бинарник декомпилируется
  Ghidra (адрес → бинарная функция), DWARF даёт адрес → исходный файл с номером строки, tree-sitter
  вырезает исходную функцию. После слияния и отсева — **~10 млн совпавших пар функций**
  (в среднем ~500 токенов на функцию).
- **Датасет TPL и корпус.** ~12 013 C/C++-проектов (GitHub + GNU/Linux); **56 342 179
  уникальных исходных функций**, эмбеддинги — в БД **FAISS**. Крупнейший корпус в области
  (у CodeCMR — лишь 10 000 функций); больший корпус сложнее и реалистичнее.
- **Тестовый SCA-набор.** 85 заметных проектов (>1K звёзд, >10 субмодулей) скомпилированы в
  **150 stripped-бинарников** под разные архитектуры/конфигурации; вручную размечены **1045
  компонентов** (по путям, заголовкам, SBOM/CMakeLists, README, лицензиям) — крупнейший
  ground-truth в binary-to-source SCA. Для 15 (10 %) наиболее ходовых бинарников вручную
  размечено соответствие функций — **23 529 пар**.

Метрики: Precision, Recall, F1; порог θ = 0,01 (максимум F1). Для поиска функций — MRR
(средний обратный ранг) и Count/Recall@k.

### 4.2. Установка эксперимента

Эмбеддинг-модель сравнивается с SOTA **CodeCMR** (раздельные кодировщики DPCNN для исходного и
GNN для бинарного кода, triplet loss). Параметры BinaryAI: макс. длина 2048, 196 эпох, батч 512,
learning rate 0,001. В сравнение включены и классические BinPro и B2SFinder (базовые признаки +
венгерский алгоритм). Инструменты SCA-сравнения: академические **OSSPolice** и **B2SFinder**,
два коммерческих **bsca-A** и **bsca-B** (анонимизированы по NDA); всем дана одна база из 12 013
проектов.

### 4.3. Результаты

**RQ1 — эффективность эмбеддингов (табл. 1).** BinaryAI превосходит CodeCMR по MRR на обоих
наборах запросов (0,3006 против 0,1431 и 0,3958 против 0,2232; объединённо 0,3407 против 0,1769)
и по Count/Recall@k. Пример (top-10, бинарный SCA-набор): BinaryAI находит 13 493 совпавшие
функции из 23 529 (recall 57,35 %), CodeCMR — 7 873 (33,46 %). recall@1 вырос с 10,75 % до
22,54 %, recall@100 — с 33,87 % до 56,60 %. Абляция: переход CodeCMR с triplet loss на CLIP
поднимает MRR 0,1431→0,2319; для BinaryAI замена CLIP на triplet ухудшает (0,3006→0,2774) —
оба фактора (LLM-база и CLIP) важны, причём BinaryAI с triplet всё равно лучше CodeCMR с CLIP
(0,2774 против 0,2319).
> **Вывод 1:** BinaryAI эффективнее CodeCMR за счёт LLM-базы и CLIP-цели обучения.
> **Вывод 2:** классические feature-matching-техники (BinPro, B2SFinder) слабы на крупном
> корпусе (MRR < 0,005, <10 % полноты в top-100) — подтверждает преимущество эмбеддинг-поиска.

**RQ2 — точность сопоставления кода (табл. 2, рис. 5).** На 15 размеченных бинарниках точность
точного совпадения (Exact Match) — **81,63 %** в среднем (от 75,19 % у turbobench до 94,92 % у
hyriseSystem), нечёткого (Fuzzy Match, после нормализации) — **95,86 %** (90–98 %). Вклад фазы
локальности: recall@1 для BinaryAI растёт с 22,73 % до 54,70 % (вход top-10, потолок 57,35 %) и
до **66,90 %** (вход top-100, потолок recall@100 = 70,45 %); для CodeCMR — с 11,92 % до 28,61 %
(top-10). То есть если модель вернула верную функцию в top-k, фаза локальности её надёжно
выводит в top-1.
> **Вывод 3:** сопоставление по локальности эффективно выделяет точную исходную функцию из top-k
> и обобщается на разные бинарники.
> **Вывод 4:** оно значительно повышает общую точность сопоставления, облегчая downstream-SCA.

**RQ3 — точность обнаружения TPL (табл. 3, рис. 6).** На 1045 компонентах в 150 бинарниках:

| Инструмент | TP | FP | FN | P (%) | R (%) | F1 (%) |
|---|---|---|---|---|---|---|
| OSSPolice | 348 | 191 | 697 | 64,56 | 33,30 | 43,94 |
| B2SFinder | 574 | 1232 | 471 | 31,78 | 54,93 | 40,26 |
| bsca-A (комм.) | 232 | 108 | 813 | 68,24 | 22,20 | 33,50 |
| bsca-B (комм.) | 625 | 227 | 420 | 73,36 | 59,81 | 65,90 |
| **BinaryAI** | **679** | **112** | **366** | **85,84** | **64,98** | **73,97** |

BinaryAI доминирует по точности и полноте на большинстве бинарников, за ним bsca-B.
Анализ ошибок: все 112 ложноположительных связаны с ограничениями TPL dependency (перекрытие
функций-признаков, не отфильтрованное TPLite); большинство ложноотрицательных (312 из 366) —
из-за **частичного переиспользования** (бинарник берёт лишь малую долю функций TPL, доля ниже
порога θ; пример: nano_node использует лишь 8 функций из leveldb).
> **Вывод 5:** BinaryAI доминирует в обнаружении TPL среди SOTA-инструментов бинарной SCA.

## 5. Угрозы валидности

- **Внутренняя:** дизайн BinaryAI. Авторы потратили >2 лет, в т. ч. пробовали обучать модель на
  структурных признаках (AST, поток управления/данных) как часть эмбеддинга — результат заметно
  хуже текущего. Код проверяли три старших инженера.
- **Внешняя:** субъекты и датасет. Сравнение с SOTA-моделью CodeCMR и четырьмя инструментами SCA;
  обучающий набор построен автокомпиляцией ArchLinux, собран крупнейший корпус и ground-truth
  (ценой большого ручного труда по разметке).
- **Конструктная:** метрики. Использован стандартный набор (MRR, Recall@k, Precision, Recall, F1).

## 6. Связанные работы

**SCA.** B2SFinder (control-flow + веса признаков), ModX (модуляризация функций), Xu et al.
(многоуровневая «birthmark»-модель против обфускации), LibDB (синтаксис + эмбеддинги функций +
фильтрация графом вызовов), OSSPolice (иерархическая индексация). Source-to-source: SourcererCC,
DéjàVu (Lopes et al.), **Centris** (сигнатура функции + TPL-зависимости по function birth time),
**TPLite** (иерархические пути + анализ центральности для фильтрации FP). Android-SCA:
ATVHunter, LibScout, LibID. BinaryAI — **первая** трансформер-модель в binary-to-source SCA;
плюс link-time locality для точности.

**Детектирование клонов кода.** Binary-to-source: CodeCMR (DPCNN + GNN). Binary-to-binary:
Asm2Vec, InnerEye, jTrans (jump-aware трансформер), Gemini (Structure2vec над ACFG), XBA
(выравнивание графов), DeepBinDiff, VulHawk.

## 7. Заключение

BinaryAI снимает проблемы избыточности базовых признаков и их нехватки между TPL и stripped-
бинарником. Трансформер-модель порождает эмбеддинги функций по токен-признакам, а сопоставление
по локальности обогащает их семантикой (link-time locality + граф вызовов) для выбора точных
совпадений; по доле совпавших функций обнаруживаются переиспользованные TPL. Эмбеддинг-модель
значительно превосходит CodeCMR (recall@1 22,54 %, MRR 0,34), а итоговое обнаружение TPL —
все существующие инструменты binary-to-source SCA. Сервис: https://www.binaryai.net.
