### Цель 1: эффективность трассировки (наше узкое место — overhead ptrace)

- **strace --seccomp-bpf** (FOSDEM 2020) — готовый инженерный рецепт: останавливать
  процесс только на open*/exec*/fork через BPF-фильтр в ядре. Buildography это уже делает,
  build-recorder — нет; самая дешёвая оптимизация из возможных.
- **Nexpoline** (arXiv 2406.07429) — перехват через Memory Protection Keys + Syscall User
  Dispatch вообще без остановки процесса трассировщиком; SUD есть в ядре с 5.11.
- **Aquila** (2025) — eBPF-телеметрия syscall целиком в ядре; ориентир при миграции на
  eBPF (вместе с уже имеющимся Bomfather), ценой требования root/CAP_BPF.

### Цель 2: обнаружение и идентификация unbuilt-бинарников

Главная находка концептуальная: обнаружить «бинарник, не собранный из исходников» мы уже
умеем (как и bxy-find-unbuilt-binaries), а вот идентифицировать его происхождение —
отдельное направление binary-to-source matching:

- **OSSPolice** (CCS 2017) → **B2SFinder** (ASE 2019) → **B2SMatcher** (2021) — эволюция:
  атрибуция бинарника к OSS-проекту по строкам/константам/control-flow, вплоть до
  определения версии. Бинарный аналог нашего git-blob-подхода для исходников — кандидат
  на «второй уровень» verify-build.
- **Rosenblum et al.** (ISSTA 2011) и **BinProv** (RAID 2022, без дизассемблирования) —
  определение компилятора/тулчейна/опций по бинарнику: для unbuilt-блоба можно сообщать
  не только «чужой», но и «чем собран».
- **CENTRIS** (ICSE 2021, код открыт) — идентификация модифицированных/вложенных
  вендоренных компонентов, 91 %/94 % precision/recall; их приём «сравнивать только
  уникальную часть компонента» может ускорить наш --upstream-verify.
- **Патент US 12067122** «Detecting added functionality in open source package» —
  формулировка почти дословно наша задача («функциональность, не описанная исходниками»).

### Поддерживающий контекст (мотивация и позиционирование статьи)

- **«Phantom binary dependencies»** — Harbuz, FOSDEM 2026 + PEP 770: 212 из топ-5000

  наша трассировка решает это динамически.

## Методика чтения статей

Не читать подряд и не читать целиком. Для нашей цели (статья + выбор техник для
verify-build) — трёхуровневая схема; база устроена под неё.

### 1. Читать с вопросом, а не «для знания»

У каждой записи в ANNOTATIONS.md есть поле «Для нас» — вопрос, ради которого статью стоит
открывать. Как только ответ получен — чтение окончено, даже если осталось 8 непрочитанных
страниц. Результат сразу фиксируется в аннотации (статус + 2–3 строки ответа).
**Аннотация — deliverable чтения**; всё, что не записано, через месяц потеряно.

### 2. Три прохода (метод Кешава), а не один сплошной

- **Проход 1 (5–10 мин):** аннотация → введение → заключение → таблицы/графики.
  Решение: «выкинуть / достаточно / читать метод». Для ~половины записей этого хватит —
  они нужны только как ссылка в related work.
- **Проход 2 (30–60 мин):** только секция метода и эксперименты, под вопрос «Для нас».
  Уровень для B2SMatcher, Nexpoline, ARES-2024.
- **Проход 3 (полное чтение с конспектом):** только прямые конкуренты и то, что
  собираемся воспроизводить: CENTRIS, патент 12067122 (читать claims, не описание),
  возможно B2SFinder. Buildography закрыт на этом уровне.

### 3. Группировать по цели, не по порядку в файле

Две сессии: «позиционирование» (конкуренты: CENTRIS, патенты, B2S*) и
«производительность» (strace-seccomp-bpf, Nexpoline, Aquila). В одной сессии мозг держит
один вопрос сравнения — различия между статьями видны резче.

### 4. Разделение труда с Claude

Паттерн: назвать ключ из ANNOTATIONS.md — Claude скачивает PDF в pdf/, извлекает текст,
делает проход 1–2 (отвечает на вопрос «Для нас», закрывает TODO по метаданным) и
говорит, стоит ли читать самому и какие разделы.

**Предостережение:** прямых конкурентов читать самому, не по пересказу — сравнение с ними
придётся защищать перед рецензентом. Выжимка Claude — карта («метод в 3.2, слабое место в
оценке — раздел 5»), не замена. Для длинного хвоста (SLR, эмпирика, frameworks) прохода
Claude достаточно.
