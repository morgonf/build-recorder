## Прямые конкуренты: build tracing

### `granat2024-buildography` — Идентификация реквизитов сборки через отслеживание системных вызовов

- **Статус:** прочитана полностью (2026-06-09); текст: `pdf/buildography-paper.pdf`
- **Категория:** ближайший конкурент, обязательна ссылка
- **Механизм:** ptrace + seccomp-BPF (SECCOMP_RET_TRACE только для open/openat/openat2; execve/fork/vfork/clone — через PTRACE_O_TRACE*-флаги). Трассировщик на Си (rhash, uthash; многопоточное отложенное хэширование с заполнителями в буфере), постпроцессор на Python. Хэши ГОСТ Р 34.11-2012 (Стрибог-256). Мотивация — ГОСТ Р 71206-2024.
- **Результаты:** замедление сборки 19–26 % (1 поток), 14–110 % (8 потоков; узкое место — однопоточная обработка ptrace-событий). Замеры: musl, qtbase × gcc, clang.
- **Признанные ограничения (в тексте):** «защита от вредоносных процессов не является целью» — подмена файла посторонним процессом не обнаруживается; ARM64 не имеет SYS_open.
- **Чего НЕТ (vs наш подход):** RPM-атрибуции; git-blob SHA-1 и сверки с `git ls-tree` upstream; идентификации вендоренных зависимостей; SBOM-форматов; CVE; иерархии процессов в выводе (массив component_commands плоский); временных меток.
- **Для статьи:** основная сравниваемая работа. Обзор отвергнутых ими альтернатив (Bear, compiledb, CDE, clang -MJ, FUSE, inotify) можно переиспользовать в related work.
- **Авторы:** студенты/лаборанты ИСП РАН + ВШЭ + СГУ (Гранат — ст. лаборант, Дунаев — аспирант) — не основная компиляторная команда.

## Эффективность перехвата системных вызовов

*Цель подборки: снизить накладные расходы build-recorder (у Buildography 14–110 %; у нас сопоставимая проблема — ptrace останавливает процесс на каждом вызове).*

### `yang2024-nexpoline` — Making `syscall` a Privilege not a Right

- **Статус:** не прочитана (найдена 2026-06-09)
- **Механизм:** Nexpoline — перехват syscall через Memory Protection Keys + Syscall User Dispatch: монитор живёт в адресном пространстве процесса, без context switch трассировщика на каждый вызов.
- **Для нас:** кандидат на радикальное снижение overhead vs ptrace; SUD (`prctl(PR_SET_SYSCALL_USER_DISPATCH)`) доступен с ядра 5.11 — реализуемо без eBPF-привилегий.

### `strace2020-seccompbpf` — strace --seccomp-bpf (FOSDEM 2020)

- **Статус:** не просмотрен
- **Механизм:** инженерное описание того, как strace с v5.3 останавливает процесс только на интересующих вызовах через seccomp-BPF (тот же приём, что у Buildography).
- **Для нас:** прямой рецепт оптимизации build-recorder — фильтровать на уровне ядра всё, кроме open*/exec*/fork/clone; ожидаемое ускорение в разы на syscall-интенсивных сборках.

### `aquila2025-telemetry` — Aquila: In-Kernel System Call Telemetry

- **Статус:** не прочитана; TODO: уточнить venue
- **Механизм:** eBPF-телеметрия системных вызовов целиком в ядре (cloud-native среды).
- **Для нас:** ориентир, если решим мигрировать с ptrace на eBPF (вместе с `bomfather2025-ebpf`); минус — требует CAP_BPF/root и теряет переносимость на старые ядра.

### `shen2024-aschook` — ASC-Hook: транспарентный syscall-хук для ARM

- **Статус:** не прочитана (найдена 2026-06-28)
- **Механизм:** гибридная замена инструкций + специальный трамплин для перехвата системных вызовов на ARM без ptrace; overhead ~3,7 %, в ~29 раз дешевле существующих инструментов.
- **Для нас:** актуально, только если build-recorder пойдёт на ARM64 (где, как отмечает Buildography, нет SYS_open); на x86_64 наш путь — SUD/seccomp (`yang2024-nexpoline`, `strace2020-seccompbpf`). Держать как ARM-ориентир.

## Идентификация компонентов: source-level

### `woo2021-centris` — CENTRIS (ICSE 2021)

- **Статус:** прочитана полностью (2026-06-09); перевод: [translations/woo2021-centris.ru.md](translations/woo2021-centris.ru.md); PDF: `pdf/woo2021-centris.pdf`
- **Механизм (после прочтения):** гранулярность — функция (ctags + нормализация + TLSH, cutoff 30). P1: сигнатура OSS = функции всех версий без повторов (redundancy elimination, сжатие пространства сравнения в 45 раз: 2,2 млрд → 49 млн функций). P2: сегментация кода — отделение «прикладного кода» OSS от заимствованного через **birth time** функций (дата релиза самой ранней версии, содержащей функцию): если общая функция S и X родилась в X раньше — X вложен в S. Компонент найден, если доля переиспользованного прикладного кода ≥ θ = 0.1. Версия — взвешенное голосование функций по IDF-весу W(f) = log(n/|V(f)|).
- **Результаты:** 91 % precision / 94 % recall (DéjàVu: <10 % / ≤40 %); версия — 91,5 % precision; <1 мин/приложение после препроцессинга. Эмпирика: 95 % переиспользований модифицированы, в среднем берут 48 % кодовой базы с 5 % правок; частичное переиспользование — 97 % случаев.
- **Чего НЕТ (vs наш подход):** не привязан к сборке — статический анализ дерева исходников; не отвечает «какие файлы реально участвовали в компиляции»; идентифицирует версию-релиз, но не произвольный коммит (наш кейс wslay = коммит между релизами им принципиально недоступен: их БД индексирует только теги/версии); точность вероятностная (порог θ), не криптографическая.
- **Для нас (ответы после прочтения):**
  1. Идея «birth time» переносима на git: наш аналог — `git log --follow` по датам появления blob-ов; можно отделять вложенные vendored-deps (их «nested» — ровно наш wslay-в-aria2 кейс).
  2. Приём сегментации применим к --upstream-verify: сравнивать только blob-ы, уникальные для компонента (не встречающиеся в других upstream-репо) — отсечёт ложную атрибуцию общих файлов (LICENSE, configure-скрипты).
  3. Их слабость = наша сила: функции из >10 смешанных версий они признают неидентифицируемыми; git-blob-сравнение с деревом коммитов решает это точно.
  4. Эмпирика «95 % модифицированы, берут 48 % кода» — готовая мотивация, почему наивное сравнение тарболов не работает; цитировать во введении.
- **Код:** https://github.com/wooseunghoon/Centris-public, сервис https://iotcube.net/

## Идентификация компонентов: binary-level (для unbuilt binaries)

*Цель подборки: что делать с бинарником, найденным в сборке, но не собранным из исходников (аналог bxy-find-unbuilt-binaries, но с идентификацией происхождения, а не только обнаружением).*

### `duan2017-osspolice` — OSSPolice (CCS 2017)

- **Статус:** проход 1 сделан (Claude, 2026-06-28); PDF: `pdf/duan2017-osspolice.pdf`. **Корень линии binary-to-source** — читать проход 1, везде пересказан (B2SFinder/B2SMatcher/BinaryAI ссылаются). Авторы: Duan, Bijlani, Xu, Kim, Lee (Georgia Tech), doi:10.1145/3133956.3134048. Открыт на GitHub.
- **Задача (двойная):** в Android-приложениях найти (1) нарушения GPL/AGPL-лицензий и (2) использование уязвимых (1-day) версий OSS. То есть атрибуция бинаря к OSS-проекту **и его версии**.
- **Механизм:** извлекает из бинаря «software birthmarks» и сравнивает с признаками, извлечёнными из **исходников** OSS (binary→source). Признаки **синтаксические**: для нативных C/C++ — строковые литералы + **экспортируемые имена функций** (дёшево, переживают оптимизацию, но не сильную обфускацию); для Java — строковые константы, нормализованные классы, function centroids (обфускация-устойчивые). Ключевая новизна — **иерархическая индексация**: сопоставление по структуре репозитория (строка → файл → каталог), отсюда масштаб и точность одновременно.
- **Масштаб/результаты:** БД 60K C/C++ + 77K Java OSS (миллиарды строк), проанализировано 1,6 млн приложений Google Play. C/C++: recall 82% / precision 87%; Java: recall 89% / precision 92% — лучше BAT и LibScout; по версиям находит на 65% больше, чем LibScout. Если точной версии нет в БД — отдаёт **ближайшую**. Эмпирика: >40K приложений нарушают GPL/AGPL, >100K используют уязвимые версии OSS.
- **Место в линии:** база на **синтаксике** (строки+символы). Её слабость к обфускации/инлайну → мотивация B2SFinder (+ control-flow), а затем BinaryAI (семантические эмбеддинги функций). Знать OSSPolice нужно как «откуда всё пошло».
- **Для нас:** базовый приём «строки + экспортируемые символы» для атрибуции unbuilt-блоба к upstream, когда трассы сборки нет по определению. **Чего НЕТ (vs наш подход):** (1) вероятностное **сходство birthmarks**, не точная провенанс-привязка; при отсутствии версии выдаёт «ближайшую» (мы — точный git-blob или честное «нет»). (2) Работает по **финальному бинарю**, входы сборки не видит — выводит постфактум. (3) Цель — Android-приложения и нарушения лицензий, не дистро-сборка.

### `feng2019-b2sfinder` — B2SFinder (ASE 2019)

- **Статус:** проход 1 сделан (Claude, 2026-06-28, по конференц-странице/конспектам — PDF за пейволлом IEEE/ACM). doi:10.1109/ASE.2019.00100. Второе звено линии после OSSPolice. TODO: полные имена авторов (PDF недоступен открыто).
- **Цель:** переиспользование OSS в **COTS** (закрытом коммерческом) ПО — шире, чем Android-приложения OSSPolice. binary→source, уровень **проекта** (версию ещё не выделяет — это вклад B2SMatcher).
- **Механизм — 7 компиляционно-устойчивых признаков в 3 категориях** (это и есть приращение над OSSPolice):
  - **строковые:** экспортируемые функции, строковые константы, строковые массивы;
  - **числовые:** глобальные массивы констант, глобальные enum-массивы;
  - **control-flow:** паттерны if-else, switch-case jump-таблицы.
  Три метода сопоставления: строковый (инвертированный индекс, точное), числовой (поиск битстрима в `.data`/`.rdata`), control-flow (сравнение семантически эквивалентных паттернов). Два веса значимости: **бинарная информационная энтропия** (для числовых) и **S-IDF** (адаптация TF-IDF).
- **Результаты:** precision 92,3% / recall 88,5%; 21 991 бинарник vs 2 189 OSS-библиотек; находит **до 2,15× больше** случаев переиспользования, чем SOTA (OSSPolice); ~53,85 с/бинарник. Вывод: 63,4% закрытого ПО переиспользует OSS.
- **Что приращено над OSSPolice (нерв линии):** OSSPolice падает, когда строки/символы не совпадают. Кейс Foxit Reader/OpenSSL: общих имён экспортируемых функций нет, строк совпало лишь 19,7% → OSSPolice пропускает. B2SFinder ловит за счёт **control-flow и числовых** признаков + взвешивания. Прогресс линии: синтаксика строк/символов (OSSPolice) → + control-flow + взвешенное сопоставление (B2SFinder) → семантические эмбеддинги (BinaryAI).
- **Для нас:** кандидат на «второй уровень» verify-build — для unbuilt-бинарника устанавливать исходный OSS-проект. **Чего НЕТ (vs наш подход):** (1) по-прежнему **вероятностное сходство** (взвешенное совпадение признаков), не точная провенанс-привязка; (2) уровень проекта, **не версии**; (3) работает по финальному бинарю, входы сборки не наблюдает.

### `b2smatcher2021-version` — B2SMatcher

- **Статус:** проход 2 сделан (Claude, 2026-06-28); PDF: `pdf/b2smatcher2021-version.pdf` (Cybersecurity, SpringerOpen, **открытый доступ**), doi:10.1186/s42400-021-00085-7. Авторы: Gu Ban, Lili Xu, Yang Xiao, Xinhua Li, Zimu Yuan, Wei Huo (Institute of Information Engineering, Chinese Academy of Sciences). **Кульминация линии — прямой конкурент по «второму уровню verify-build», читать самому** (Design §, особенно предсказание скомпилированных файлов и two-stage).
- **Цель:** не просто проект, а **точная ВЕРСИЯ** переиспользованной OSS в COTS-бинарнике. Мотивация — 1-day-уязвимости версионно-специфичны (Heartbleed = OpenSSL 1.0.1–1.0.1g). Берёт кандидатов от OSSPolice/B2SFinder и доводит до версии.
- **Почему прошлых признаков мало:** строки/символы (OSSPolice) и глобальные массивы/control-flow (B2SFinder) **не различают соседние версии** и дают высокие FP при version-identification. Нужны **version-sensitive** признаки.
- **Метод — 5 признаков на двух уровнях + two-stage:**
  - **program-level (2):** строковые литералы, экспортируемые имена функций → этап 1, грубое сопоставление + определение типа переиспользования;
  - **function-level (3):** константы в присваиваниях, константные параметры вызовов, in/out-степени функции на call-graph → этап 2, точное доведение до версии (ловит правки в отдельных функциях между соседними версиями).
- **Два ключевых приёма:**
  1. **ML-предсказание скомпилированных файлов.** Проблема partial build: в бинарь попадает лишь часть исходников (у zlib — **7,3%** файлов), признаки остальных только шумят. Хукать сборку (как Duan 2019) для COTS нельзя — исходники/сборка недоступны. Поэтому **K-means + дерево решений** предсказывают, какие файлы реально компилировались, и признаки берут только из них.
  2. **Абстракция+нормализация функций** — выкинуть дублирующиеся между версиями функции, сравнивать только «уникальные» (масштаб).
- **Новизна — тип переиспользования:** single-version vs **multi-version reuse** (патчинг). Пример: SQLite в одном dll — это 3.6.15, поверх которого добавлены функции из 3.8.8.3. Решение — комбинировать совпавшие признаки И сходство, а не сходство в одиночку.
- **Оценка:** 6351 версия OSS, 585 бинарников (ручная сборка + реальный софт). Precision **89,2%** — выше B2SFinder, +8% к OSSPolice, +7% к коммерческому Cybellum. Нашли уязвимые версии OSS в Zoom, TeamViewer (libcurl 7.65.3 c CVE-2019-5481/5842, zlib 1.2.5, libjpeg-turbo 8b), Tencent.
- **Пределы (Discussion):** инлайн ломает call-graph-степени (деградация function-level); набор скомпилированных файлов зависит от опций (макросы) — при сильно нестандартном конфиге предсказание хуже; признаки выбраны вручную (будущее — семантические, ср. путь BinaryAI).
- **Для нас (сильный контраст):** B2SMatcher **угадывает ML-ом то, что мы наблюдаем точно**. Их центральная трудность — «какие исходные файлы вошли в бинарь» (partial build, 7,3% у zlib) — решается у них вероятностно, потому что сборка COTS вне досягаемости. build-recorder **трассирует фактическую сборку** и знает точный список вошедших файлов как ground truth; они сами называют build-hooking точным путём (Duan 2019), но отвергают из-за недоступности — у нас он доступен по построению. **Чего НЕТ (vs наш подход):** (1) версия как **наиболее вероятная по сходству**, не точный git-blob; multi-version/патчинг — эвристика; (2) ML-предсказание компиляции вместо наблюдения (наш ground truth — их оценка); (3) по финальному бинарю. Это и есть бинарный аналог нашего git-blob-уровня — но вероятностный там, где мы точны.

### `rosenblum2011-toolchain` — Recovering the toolchain provenance of binary code (ISSTA 2011)

- **Статус:** проход 1 сделан (Claude, 2026-06-28, по конф-странице/Semantic Scholar/Vestige — PDF за пейволлом ACM). doi:10.1145/2001420.2001433. Авторы: Nathan E. Rosenblum, Barton P. Miller, Xiaojin Zhu (UW-Madison). **Корень под-ветки тулчейна** («чем собрано», не «что собрано»).
- **Цель:** восстановить **toolchain provenance** бинаря — семейство компилятора (gcc/icc/msvc), а в развитии линии и версию + уровень оптимизации.
- **Механизм:** дизассемблирует IA-32, извлекает **idiom-признаки** (короткие шаблоны инструкций вокруг точек входа функций, FEP) + признаки структуры control-flow; обучает **linear-chain Conditional Random Fields (CRF)**, которые **совместно** моделируют provenance по всему бинарю (используют, что соседний код имеет общее происхождение). Предшественник — их же PLDI'2010 «Extracting compiler provenance» (более простые линейные модели).
- **Результаты:** распознавание семейства компилятора с точностью **~0,925**. Развитие (CFG-признаки + SVM) доводит до полной provenance (семейство + версия + оптимизация).
- **Для нас:** для unbuilt-блоба сообщать не только «чужой», но и «чем собран» — проверка заявлений поставщика (наш `readelf -p .comment` для SAFEC-сборок — тривиальный частный случай). **Чего НЕТ (vs наш подход):** (1) вероятностная **оценка по признакам**, требует дизассемблирования и ручных idiom-фич; (2) выводит компилятор постфактум из бинаря — мы **наблюдаем** фактическую команду компиляции (точная версия gcc + флаги из трассы) как ground truth.

### `binprov2022` — BinProv (RAID 2022)

- **Статус:** проход 1 сделан (Claude, 2026-06-28, по сводкам GMU/конф — PDF за Cloudflare/пейволлом). doi:10.1145/3545948.3545956. Авторы: Xu He, Shu Wang, Yunlong Xing, Pengbin Feng, Haining Wang, Qi Li, Songqing Chen, Kun Sun (GMU и др.). **ML-эндпоинт под-ветки тулчейна** (аналог BinaryAI для линии «чем собрано»).
- **Цель:** идентификация provenance — компилятор + версия + **уровень оптимизации O0/O1/O2/O3**.
- **Механизм:** **BERT**-эмбеддинги прямо по **байтам** бинаря (контекстная семантика/синтаксис), **без дизассемблирования** и без ручного отбора признаков; дообучение классификатора под конкретную задачу provenance. Это и есть главный шаг над Rosenblum (там нужны IA-32-дизасм + рукодельные idioms).
- **Результаты:** точность **92,14% / 99,4% / 99,8%** на уровне байтовой последовательности / функции / бинаря соответственно. Работает и на обфусцированных бинарях; полезно для опознания compiler-helper-функций и улучшения binary similarity.
- **Место в под-ветке:** Rosenblum'11 (дизасм + idioms + CRF) → BinProv'22 (сырые байты + BERT, без дизасма) — та же эволюция «ручные признаки → выученные представления», что и в основной линии (OSSPolice→BinaryAI), но для тулчейна.
- **Для нас:** дешёвый массовый способ узнать «чем собран» каждый blob сборки. **Чего НЕТ (vs наш подход):** (1) вероятностный классификатор по байтам, не наблюдение; (2) даёт компилятор/опции с вероятностью — у нас точная команда из трассы. Тот же контраст «угадывание vs наблюдение», что во всей линии.

### `jiang2024-binaryai` — BinaryAI (ICSE 2024)

- **Статус:** проход 1–2 сделан (Claude, 2026-06-28); перевод-конспект: [translations/jiang2024-binaryai.ru.md](translations/jiang2024-binaryai.ru.md); PDF: `pdf/jiang2024-binaryai.pdf`. Как прямого конкурента — прочитать самому (метод 3.3 locality-driven matching, оценка RQ3).
- **Механизм:** binary-to-source SCA в две фазы. (1) Эмбеддинги функций: модель на базе Pythia-410M, дообучена контрастно (CLIP loss + MoCo), извлекает top-k похожих исходных функций для каждой бинарной (декомпиляция Ghidra, парсинг tree-sitter, корпус 56 млн функций из 12 013 TPL в FAISS). (2) Locality-driven matching: link-time locality (непрерывность функций одного исходного файла в бинарнике, задача покрытия интервалами) + граф вызовов выбирают точную функцию из top-k. TPL-фильтрация через TPLite (function birth time). Порог θ=0,01.
- **Интуиция (что такое «вектор функции»):** эмбеддинг — список из 1024 чисел (выход pythia-410m), точка в 1024-мерном пространстве; кодируется **целая функция**, не инструкции. Обе стороны — псевдо-C от Ghidra и исходник — кодирует одна модель в общее пространство, сходство = косинус между векторами (1,0 — совпали, 0 — не связаны). Пример из статьи (рис. 3): бинарная `FUN_00153d7b` и исходная `DefaultLogDir()` (glog) при разных именах переменных и структуре `if` дают косинус 0,982. Матчинг **семантический**: не по именам (бинарник stripped, имён нет) и не по AST (AST через tree-sitter — только чтобы нарезать исходники на функции, в сопоставлении не участвует). Итоговое «бинарник содержит X» = доля функций X, нашедшихся в бинарнике, > θ.
- **Результаты:** recall@1 модели 22,54 % vs CodeCMR 10,75 %; locality-matching поднимает recall@1 до 66,90 % (потолок 70,45 %). TPL-детект: P 85,84 % / R 64,98 % / F1 73,97 % — обходит академические OSSPolice, B2SFinder и оба коммерческих bsca-A/B. FN в основном (312/366) — частичное переиспользование (доля функций < θ).
- **Методологические оговорки (не брать 85,84 % как реальную метрику):**
  1. **Порог θ=0,01 подобран на тесте** («set θ to 0.01 that achieves the maximum F1 score») — решающий порог тюнингован на том же наборе, где меряют F1, без held-out; пороги бейзлайнов так не оптимизировали (асимметрия). θ=0,01 экстремально низкий (TPL засчитывается при совпадении 1 % функций) — задирает recall, FP-потоп гасится TPLite.
  2. **Асимметрия антиклонового фильтра без абляции.** У BinaryAI есть стадия `FilterByDependency` (TPLite) против функций-клонов, общих между TPL; не сказано, что её дали бейзлайнам. Раздутый FP B2SFinder (1232 > TP 574) скорее всего во многом артефакт отсутствия этого фильтра, а не качества признаков. Нет абляции «BinaryAI без TPLite vs бейзлайны с TPLite» → вклад эмбеддингов/локальности и вклад фильтра в преимущество по точности неразделимы. Бейзлайны вдобавок запущены вне режима (B2SFinder извлекает 1 функцию из корпуса 56 млн — в 5600× больше его проектного масштаба; переписан авторами).
  3. **Генерализация за пределы обучающего тулчейна не показана (не «только Arch»).** Обучающие пары «бинарная↔исходная функция» взяты из ArchLinux/AUR их же пайплайном (makepkg, DWARF) и декомпилированы **Ghidra**; исходный корпус (12 013 TPL) — общий OSS, не Arch-специфичен. И train, и test декомпилированы Ghidra (лок-ин на идиомы конкретного декомпилятора) и скомпилированы авторами фактически gcc-тулчейном Arch (≈-O2, x86_64). Test заявляет «multiple architectures and compiler configurations», но **разбивки по компиляторам/оптимизациям/архитектурам нет** — не показано, что точность держится на MSVC/PE, тяжёлом LTO/-O3, обфускации, не-Ghidra декомпиляции. То есть метрики получены на распределении тулчейна, близком к обучению; для широкого класса «Linux ELF из mainstream-gcc через Ghidra» вероятно обобщается, для чужих компиляторов/декомпиляторов — terra incognita. Вдобавок корпус = вселенная теста (компоненты popular >1K звёзд, гарантированно в базе; длинный хвост недопредставлен), ground truth целиком self-compiled/self-labeled без слепой разметки.
- **Доступность:** proprietary-платформа Tencent (Cloud Security / Keen Lab). В тексте статьи **нет artifact-availability заявления** — не выложены ни веса модели (Pythia-410M + дообучение), ни корпус 56 млн функций / датасет 12 013 TPL, ни обучающий набор (~10 млн пар), ни размеченный SCA-тест (150 бинарников, 1045 компонентов), ни код пайплайна. Публичны лишь хостовый сервис (binaryai.cn/single-file, ≤20 МБ) и API — чёрный ящик. Открыты только зависимости (Ghidra, tree-sitter, Pythia, FAISS), не сборка. `binaryai/CodeCMR` на GitHub — данные бейзлайна-конкурента, не BinaryAI. Коммерческие bsca-A/bsca-B анонимизированы по NDA. **Итог:** заявленные 85,84 % независимо неверифицируемы (нет данных/модели/кода) — для related work отмечать как proprietary, артефакты не опубликованы.
- **Открытые инструменты, используемые в статье** (контраст к закрытости самого BinaryAI — алгоритм собран из открытых кирпичей, но без их корпуса/весов не реплицируем):
  - *Пайплайн:* **Ghidra** (декомпиляция, NSA, Apache 2.0), **tree-sitter** (парсинг исходников, MIT), **Pythia-410m** (базовая LLM, EleutherAI, Apache 2.0; ранее пробовали **OPT**, **BLOOM**), **FAISS** (векторный поиск, Meta, MIT), **makepkg** (сборка обучающих пакетов ArchLinux/AUR, GPL).
  - *Методы/алгоритмы:* **CLIP** (контрастная цель), **MoCo** (расширение негативов), **Hungarian algorithm** (для бейзлайнов).
  - *Форматы/БД:* **DWARF** (адрес→исходник в обучении), **ArchLinux/AUR** (источник пар), **NVD** (уязвимости).
  - *Бейзлайны:* **OSSPolice** ✅ полностью (`github.com/osssanitizer/osspolice`); **TPLite** ✅ (генерирует TPL-dependency; `github.com/Tricker-z/TPLite`, ISSTA'23); **B2SFinder** ⚠️ частично — только ядро без БД/пайплайна (`github.com/1dayto0day/B2SFinder`); **CodeCMR** ⚠️ только данные (`github.com/binaryai/CodeCMR`); **BinPro** ❓ репозиторий не найден (arXiv 1711.00830, U. Toronto).
  - *Закрыто:* bsca-A/bsca-B (анонимизированы по NDA), сам BinaryAI.
- **Контраст для нас:** наш ground truth — точное git-blob-совпадение из трассировки фактической сборки: не зависит от курируемого корпуса (нечего «не найти»), от подобранного порога (совпадение точное, не доля функций) и от качества декомпиляции; не проседает на длинном хвосте. BinaryAI решает обратную, принципиально более шумную задачу (восстановить исходник из stripped-бинарника) — мы наблюдаем входы компилятора напрямую. Формулировка для статьи: **вектор отвечает на вопрос «на что похоже?», git-blob-хеш — «что это ровно такое?»** (косинус 0,98 ≠ тождество: разные функции могут дать 0,95, та же при -O3 — 0,7; у нас blob либо побитово равен upstream-коммиту, либо нет).
- **Чего НЕТ (vs наш подход):** привязки к сборке — это статический анализ готового бинарника, не наблюдение компиляции; не git-blob-точность, а вероятностное совпадение функций; не атрибутирует версию/коммит, только факт переиспользования библиотеки.
- **Для нас:** state-of-the-art «второго уровня» verify-build для unbuilt-бинарников (продолжает OSSPolice→B2SFinder→B2SMatcher); цитировать как сильнейший ML-baseline бинарной идентификации.

### `ron2026-zkcompile` — Verifiable Provenance via Zero-Knowledge Compilation (2026)

- **Статус:** проход 1–2 сделан (Claude, 2026-06-28); перевод-конспект: [translations/ron2026-zkcompile.ru.md](translations/ron2026-zkcompile.ru.md); PDF: `pdf/ron2026-zkcompile.pdf`. Прямой соседний путь — прочитать самому (модель угроз §III, оговорка §VIII.B).
- **Механизм:** компилятор исполняется внутри zkVM (арифметизация трассы → полиномиальные ограничения), на выходе — ассемблер + краткое криптодоказательство («receipt»: доказательство + SHA-256 исходника + выход), что компиляция выполнена над заявленным исходником заявленным компилятором. Проверяется кем угодно без пересборки и без доверия железу. 4 свойства контрят 4 угрозы: целостность исходника (дайджест), компилятора (ImageID), выхода, свежесть (anti-replay).
- **Прототип COSMIC TURTLE:** zkVM **RISC Zero** + учебный C-компилятор **ChibiCC** (~10K строк, подмножество C), кросс-компилирован в RISC-V. Открыт: github.com/ASSERT-KTH/verifiable-compilation. Оценка: 200 программ Csmith + 31 файл OpenSSL + 21 libsodium. Все adversarial-тесты (подмена компилятора/исходника/выхода, replay) корректно отклонены.
- **Методологические оговорки (сильно ограничивают «applicable to real-world»):**
  1. **Игрушечный компилятор, подмножество C.** ChibiCC ~10K строк, без inline-asm/GNU-расширений/сложных макросов. Реальные gcc/clang — миллионы строк с оптимизациями; арифметизация их в zkVM на порядки дороже. «Реальные» libsodium/OpenSSL — это **отдельные совместимые .c-файлы**, отобранные вручную, не сами библиотеки.
  2. **Выход — ассемблер, не итоговый бинарник.** Доказывается один шаг исходник→.s одной единицы трансляции. Ассемблирование, **компоновка**, многофайловая сборка пакета (тысячи TU + линковка + build-система) — вне доказательства.
  3. **Overhead ~10 000× + receipt до 120 МБ** на один мелкий файл (медиана zk-компиляции 78,9 с против 0,009 с; проверка ~50 с). Для реального пакета пока непрактично; авторы признают «substantial», списывают на разовость и будущий прогресс zkVM.
  4. **Handshake всё равно требует бутстрап-доверия** к ImageID компилятора (рекурсию «кто собрал компилятор» отложили — самоироничная ссылка [22] на саму статью). Контрится подмена компилятора *после* согласования, но не скомпрометированный *согласованный* компилятор (Thompson trusting-trust).
  5. **zero-knowledge не нужен** (§VIII.B сами авторы): всё публично, zkVM — просто генератор кратких доказательств; по сути это succinct proof-of-execution, а не ZK как таковой.
  6. **Структурный разрыв ISA: x86-64 (боевой) vs RISC-V (доказательный).** zkVM арифметизируют RISC-V (фиксированная длина, ~50 простых инструкций), а не x86-64 — CISC с переменной длиной 1–15 байт, микрокодом и сотнями инструкций арифметизировать на порядки дороже, поэтому нативного x86 zkVM по сути нет (RISC Zero, SP1, Jolt — все RISC-V). Но реальные дистрибутивы (ALT, Debian, Arch) собирают пакеты под **x86-64**. Значит доказывается компиляция *не того* бинарника, что лежит в репозитории (RISC-V вместо x86-64), либо нужен x86-эмулятор поверх RISC-V внутри zkVM — ещё множитель к 10 000× overhead. В прототипе обойдено тем, что выход — ассемблер игрушечного ChibiCC, а не финальный x86-ELF (см. п. 2). Это не деталь реализации, а ограничение подхода — сильный довод для рецензента.
- **Для нас:** свежайший конкурирующий путь к доверенной сборке — пара к `attestable2025-tee` (TEE, аппаратный) и `lamb2021-reproducible`. Явно противопоставляет себя `jiang2024-binaryai` и `duan2017-osspolice` («post-hoc similarity, не гарантия») — здесь они **наш союзник** в аргументе «сходство/пересборка слабы». Но для позиционирования это **конкурент по доверию**: контраст «криптодоказательство одной компиляции игрушечного компилятора при 10 000× overhead vs практическое наблюдение фактической многошаговой сборки реальным gcc с атрибуцией каждого входа (RPM/git-blob)». Они дают криптостойкость на игрушечном масштабе; мы — полную атрибуцию реальной сборки без криптодоказательства нетампертинга (доверяем трассировщику). Оси ортогональны → возможна комбинация.

### `drexel2025-archverifier` — Independent Verifier for Arch Linux (2025)

- **Статус:** проход 1–2 сделан (Claude, 2026-06-28); подробный конспект: [translations/drexel2025-archverifier.ru.md](translations/drexel2025-archverifier.ru.md); PDF: `pdf/drexel2025-archverifier.pdf`. **Не прямой конкурент — самому читать не обязательно** (школа rebuild-and-compare, не атрибуция); ценно полем «Для нас» (certbot-кейс).
- **Тип:** наполовину обзор-туториал (R-B / bootstrappable builds / Diverse Double-Compiling за 10 лет), наполовину инженерный вклад. Венью — **SICHERHEIT 2024** (GI/LNI, doi:10.18420/sicherheit2024_016), arXiv-препринт 2505.21642 выложен май 2025 (отсюда «2025» в ключе; фактически работа 2024 г.). Авторы — HSLU (Люцерна) + ETH Zürich.
- **Обзорная часть (полезные числа для введения):** причины невоспроизводимости из 422 задокументированных кейсов — таймстемпы 30%, рандомизация 17%, пути 16%. Доли воспроизводимости (ноябрь 2023): Debian 95,2% (Bookworm/amd64), Arch 75,8%. Инструментарий школы: `diffoscope` (бинарный diff в читаемый вид), `rebuilderd` (kpcyrd) — демон, раздающий пересборку воркерам и отдающий статус GOOD/BAD/UNKWN.
- **Вклад (новое в статье):**
  1. Развёрнут независимый верификатор Arch на rebuilderd (reproducible.crypto-lab.ch): sync-демон тянет пакеты каждые 5 мин, воркеры пересобирают и сравнивают побитово. Воркеру нужно ≥32 ГБ RAM на все пакеты, ≥64 ГБ + tmpfs на крупные (ядро, браузеры).
  2. **Certbot — 16 пакетов невоспроизводимы.** Корень: функция `pkgver()` в PKGBUILD меняет описание сборки **после** того, как зависимости уже скачаны и установлены; в SBOM-файл `.BUILDINFO` записывается версия зависимости `python-acme`, не совпадающая с той, что реально требует PKGBUILD. Critical-софт (TLS-сертификаты Let's Encrypt). Предложение: пропатчить тулчейн Arch, чтобы он падал, если функция меняет build-описание после установки зависимостей.
  3. **fwupd — embedded-таймстемп** в заголовке gzip-файла (генерировался Python-stdlib `gzip`, а не GNU `gzip`, потому и проскользнул мимо). Отправили upstream-патч, принят.
- **Для нас (сильный довод, не просто эмпирика):** certbot-кейс — это **ровно наш аргумент «декларативный SBOM врёт, фактическая трассировка — нет»**. `.BUILDINFO` (SBOM) зафиксировал версию `python-acme`, отличную от реально использованной. build-recorder записал бы **фактический** вход компилятора/сборки, а не задекларированную версию — рассинхрон такого рода у нас невозможен по построению. Брать в введение как живой пример провенанс-бага в SBOM. Плюс свежая эмпирика «воспроизводимость на практике трудна» (Arch всего 75,8%) усиливает контраст `lamb2021-reproducible`.
- **Чего НЕТ (vs наш подход):** (1) школа **rebuild-and-compare** — нужна вторая независимая сборка + побитовое сравнение; мы атрибутируем **единственную** фактическую сборку без пересборки. (2) Сборка — чёрный ящик: сравниваются выходы (diffoscope), внутрь шага (какие именно байты/файлы вошли) не смотрят — это и есть наша ниша syscall-трассировки. (3) Атрибуции «этот блоб ← это git-дерево» нет; невоспроизводимость показывает «расходится», но не «чей вход виноват» без ручного diff.

- **Их сильная сторона:** применим post-hoc к уже опубликованному пакету; наша трассировка требует присутствия при сборке. Подходы комплементарны.
- **Для статьи:** контраст «rebuild & compare (требует воспроизводимости — исключена из SLSA 1.0) vs наблюдение фактической сборки». В их prior art цитируется OSSPolice (`duan2017-osspolice`).
