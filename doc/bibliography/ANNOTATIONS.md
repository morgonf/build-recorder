## Прямые конкуренты: build tracing

### `granat2024-buildography` — Идентификация реквизитов сборки через отслеживание системных вызовов

- **Статус:** прочитана полностью (2026-06-09); текст: `pdf/buildography-paper.pdf`
- **Категория:** ближайший конкурент, обязательна ссылка
- **Механизм:** ptrace + seccomp-BPF (SECCOMP_RET_TRACE только для open/openat/openat2; execve/fork/vfork/clone — через PTRACE_O_TRACE*-флаги). Трассировщик на Си (rhash, uthash; многопоточное отложенное хэширование с заполнителями в буфере), постпроцессор на Python. Хэши ГОСТ Р 34.11-2012 (Стрибог-256). Мотивация — ГОСТ Р 71206-2024.
- **Результаты:** замедление сборки 19–26 % (1 поток), 14–110 % (8 потоков; узкое место — однопоточная обработка ptrace-событий). Замеры: musl, qtbase × gcc, clang.
- **Признанные ограничения (в тексте):** «защита от вредоносных процессов не является целью» — подмена файла посторонним процессом не обнаруживается; ARM64 не имеет SYS_open.
- **Чего НЕТ (vs наш подход):** RPM-атрибуции; git-blob SHA-1 и сверки с `git ls-tree` upstream; идентификации вендоренных зависимостей; SBOM-форматов; CVE; иерархии процессов в выводе (массив component_commands плоский); временных меток.
- **Для статьи:** основная сравниваемая работа. Обзор отвергнутых ими альтернатив (Bear, compiledb, CDE, clang -MJ, FUSE, inotify) можно переиспользовать в related work.
- **Авторы:** студенты/лаборанты ИСП РАН + ВШЭ + СГУ (Гранат — ст. лаборант, Дунаев — аспирант) — не основная компиляторная команда.

### `ispras2024-buildography-manual` — Buildography v1.2.3, руководство

- **Статус:** прочитано полностью (2026-06-09); текст: `pdf/buildography-manual-1.2.3.pdf`
- **Механизм/детали поставки:** CLI `buildography [opts] <prog> [args]`; опции `-d/--dump-dir`, `-f/--filter-subtree`, `-T/--threads`. JSON: `directory`, `commands`, `component_commands[{command, dependencies, output}]`, `input`, `utilities[{path, hash}]`. Имя выходного файла = Стрибог-хэш его содержимого. Анализаторы: `bxy-find-unbuilt-binaries` (ELF/ar, кастомный `--is-binary-pred`), `bxy-find-external-sources`, `bxy_trace_origins` (отчёт plain/PDF через typst). Постпроцессор `bxy_postprocessor` имеет пустые точки расширения get_version/get_config_files_info.
- **Платформы:** AMD64, ARM64; ядро ≥ 4.8 с CONFIG_SECCOMP_FILTER; librhash ≥ 1.3.8, python3, jq. Протестировано: autotools+make, CMake, Meson. Распространяется бинарным tarball в /opt/buildography, лицензия ИСП РАН (закрытый).
- **Статус проекта на июнь 2026:** v1.2.3 (2024-11-20) — последняя публичная; в safec-announce 2025–2026 не упоминается; докладов на OS DAY 2025/2026 и цитирований статьи не найдено. Страница: https://www.ispras.ru/technologies/buildography/ (en-версия — заглушка).

## Эффективность перехвата системных вызовов

*Цель подборки: снизить накладные расходы build-recorder (у Buildography 14–110 %; у нас сопоставимая проблема — ptrace останавливает процесс на каждом вызове).*

### `yang2024-nexpoline` — Making `syscall` a Privilege not a Right

- **Статус:** не прочитана (найдена 2026-06-09)
- **Механизм:** Nexpoline — перехват syscall через Memory Protection Keys + Syscall User Dispatch: монитор живёт в адресном пространстве процесса, без context switch трассировщика на каждый вызов.
- **Для нас:** кандидат на радикальное снижение overhead vs ptrace; SUD (`prctl(PR_SET_SYSCALL_USER_DISPATCH)`) доступен с ядра 5.11 — реализуемо без eBPF-привилегий.

### `strace2020-seccompbpf` — strace --seccomp-bpf (FOSDEM 2020)

- **Статус:** не просмотрен
- **Механизм:** инженерное описание того, как strace с v5.3 останавливает процесс только на интересующих вызовах через seccomp-BPF (тот же приём, что у Buildography).
- **Для нас:** прямой рецепт оптимизации build-recorder — фильтровать на уровне ядра всё, кроме open*/exec*/fork/clone; ожидаемое ускорение в разы на syscall-интенсивных сборках.

### `aquila2025-telemetry` — Aquila: In-Kernel System Call Telemetry

- **Статус:** не прочитана; TODO: уточнить venue
- **Механизм:** eBPF-телеметрия системных вызовов целиком в ядре (cloud-native среды).
- **Для нас:** ориентир, если решим мигрировать с ptrace на eBPF (вместе с `bomfather2025-ebpf`); минус — требует CAP_BPF/root и теряет переносимость на старые ядра.

### `shen2024-aschook` — ASC-Hook: транспарентный syscall-хук для ARM

- **Статус:** не прочитана (найдена 2026-06-28)
- **Механизм:** гибридная замена инструкций + специальный трамплин для перехвата системных вызовов на ARM без ptrace; overhead ~3,7 %, в ~29 раз дешевле существующих инструментов.
- **Для нас:** актуально, только если build-recorder пойдёт на ARM64 (где, как отмечает Buildography, нет SYS_open); на x86_64 наш путь — SUD/seccomp (`yang2024-nexpoline`, `strace2020-seccompbpf`). Держать как ARM-ориентир.

## Идентификация компонентов: source-level

### `woo2021-centris` — CENTRIS (ICSE 2021)

- **Статус:** прочитана полностью (2026-06-09); перевод: [translations/woo2021-centris.ru.md](translations/woo2021-centris.ru.md); PDF: `pdf/woo2021-centris.pdf`
- **Механизм (после прочтения):** гранулярность — функция (ctags + нормализация + TLSH, cutoff 30). P1: сигнатура OSS = функции всех версий без повторов (redundancy elimination, сжатие пространства сравнения в 45 раз: 2,2 млрд → 49 млн функций). P2: сегментация кода — отделение «прикладного кода» OSS от заимствованного через **birth time** функций (дата релиза самой ранней версии, содержащей функцию): если общая функция S и X родилась в X раньше — X вложен в S. Компонент найден, если доля переиспользованного прикладного кода ≥ θ = 0.1. Версия — взвешенное голосование функций по IDF-весу W(f) = log(n/|V(f)|).
- **Результаты:** 91 % precision / 94 % recall (DéjàVu: <10 % / ≤40 %); версия — 91,5 % precision; <1 мин/приложение после препроцессинга. Эмпирика: 95 % переиспользований модифицированы, в среднем берут 48 % кодовой базы с 5 % правок; частичное переиспользование — 97 % случаев.
- **Чего НЕТ (vs наш подход):** не привязан к сборке — статический анализ дерева исходников; не отвечает «какие файлы реально участвовали в компиляции»; идентифицирует версию-релиз, но не произвольный коммит (наш кейс wslay = коммит между релизами им принципиально недоступен: их БД индексирует только теги/версии); точность вероятностная (порог θ), не криптографическая.
- **Для нас (ответы после прочтения):**
  1. Идея «birth time» переносима на git: наш аналог — `git log --follow` по датам появления blob-ов; можно отделять вложенные vendored-deps (их «nested» — ровно наш wslay-в-aria2 кейс).
  2. Приём сегментации применим к --upstream-verify: сравнивать только blob-ы, уникальные для компонента (не встречающиеся в других upstream-репо) — отсечёт ложную атрибуцию общих файлов (LICENSE, configure-скрипты).
  3. Их слабость = наша сила: функции из >10 смешанных версий они признают неидентифицируемыми; git-blob-сравнение с деревом коммитов решает это точно.
  4. Эмпирика «95 % модифицированы, берут 48 % кода» — готовая мотивация, почему наивное сравнение тарболов не работает; цитировать во введении.
- **Код:** https://github.com/wooseunghoon/Centris-public, сервис https://iotcube.net/

## Идентификация компонентов: binary-level (для unbuilt binaries)

*Цель подборки: что делать с бинарником, найденным в сборке, но не собранным из исходников (аналог bxy-find-unbuilt-binaries, но с идентификацией происхождения, а не только обнаружением).*

### `duan2017-osspolice` — OSSPolice (CCS 2017)

- **Статус:** не прочитана
- **Механизм:** идентификация OSS-компонентов и их уязвимых версий в бинарниках (Android) по строкам и экспортируемым именам функций; масштабируемая иерархическая индексация.
- **Для нас:** базовый подход «строки + символы» для атрибуции unbuilt-бинарника к upstream-проекту, когда трассы его сборки нет по определению.

### `feng2019-b2sfinder` — B2SFinder (ASE 2019)

- **Статус:** не прочитана
- **Механизм:** binary-to-source matching: строки, целочисленные константы, control-flow с весовыми алгоритмами; 2.15× больше найденных переиспользований, ~54 с/бинарник.
- **Для нас:** кандидат на «второй уровень» verify-build: для каждого unbuilt-бинарника пытаться установить исходный OSS-проект и версию.

### `b2smatcher2021-version` — B2SMatcher

- **Статус:** не прочитана
- **Механизм:** развитие B2SFinder до fine-grained идентификации ВЕРСИИ OSS в бинарнике.
- **Для нас:** идентификация версии — ровно то, что мы делаем для вендоренных исходников через git-blob; это бинарный аналог.

### `rosenblum2011-toolchain` — Recovering the toolchain provenance of binary code (ISSTA 2011)

- **Статус:** не прочитана
- **Механизм:** ML по последовательностям машинного кода → компилятор, версия, опции компиляции, исходный язык бинарника.
- **Для нас:** для unbuilt-бинарника можем сообщать не только «чужой», но и «чем собран» — проверка заявлений поставщика (ср. наш readelf -p .comment для SAFEC-сборок — тривиальный частный случай).

### `binprov2022` — BinProv (RAID 2022)

- **Статус:** не прочитана
- **Механизм:** идентификация provenance бинарного кода без дизассемблирования (end-to-end на байтах).
- **Для нас:** более дешёвый вариант предыдущего, пригодный для массовой обработки всех blob-ов сборки.

### `jiang2024-binaryai` — BinaryAI (ICSE 2024)

- **Статус:** не прочитана (найдена 2026-06-28); прямой конкурент — читать самому
- **Механизм:** binary-to-source SCA в две фазы: transformer-эмбеддинги функций (контрастное обучение на базе Pythia) ищут похожие исходные функции для каждой функции бинарника, затем link-time locality агрегирует совпадения в обнаружение переиспользованных TPL. Обходит коммерческий Black Duck (TPL precision 73→86 %, recall 60→65 %).
- **Чего НЕТ (vs наш подход):** привязки к сборке — это статический анализ готового бинарника, не наблюдение компиляции; не git-blob-точность, а вероятностное совпадение функций; не атрибутирует версию/коммит, только факт переиспользования библиотеки.
- **Для нас:** state-of-the-art «второго уровня» verify-build для unbuilt-бинарников (продолжает OSSPolice→B2SFinder→B2SMatcher); цитировать как сильнейший ML-baseline бинарной идентификации.

### `kim2025-bm25sca` — Cross-language binary-source SCA via BM25 (IJIS 2025)

- **Статус:** не прочитана (найдена 2026-06-28); TODO: достать PDF, полные имена авторов
- **Механизм:** binary-source SCA для пяти языков (C/C++, Objective-C, Swift, Go) и трёх типов бинарников; вместо дорогих эмбеддингов — BM25-токены, дешевле по вычислениям; recall до 81,4 %.
- **Чего НЕТ (vs наш подход):** то же, что у BinaryAI — статический матчинг бинарника без трассировки сборки и без git-blob/коммит-точности.
- **Для нас:** новейшее в линейке binary-to-source; интересен контраст «дешёвый BM25 vs дорогой transformer (BinaryAI)» при сопоставимом recall.

## Frameworks: attestation / reproducible builds

### `torres2019-intoto` — in-toto (USENIX Security 2019)

- **Статус:** не прочитана (знаю по контексту)
- **Механизм:** криптографически подписанные attestations каждого шага supply chain; «кто что сделал».
- **Чего НЕТ:** не смотрит ВНУТРЬ шага сборки — шаг доверен, если подписан; происхождение отдельных файлов не верифицируется.
- **Для нас:** комплементарен: наш вывод мог бы стать payload in-toto attestation (предикат для SLSA provenance).

### `lamb2021-reproducible` — Reproducible Builds (IEEE Software)

- **Статус:** не прочитана (знаю по контексту)
- **Суть:** бинарная воспроизводимость как способ верификации сборки.
- **Чего НЕТ:** требует детерминированной сборки (на практике трудно; выкинуто из SLSA 1.0); наша трассировка работает с любой сборкой as-is.

### `attestable2025-tee` — Attestable builds (TEE)

- **Статус:** не прочитана
- **Механизм:** верифицируемые бинарники через сборку в trusted execution environment на недоверенных системах.
- **Для нас:** альтернативный (аппаратный) путь к той же цели; контраст: мы не требуем спец-железа.

### `ron2026-zkcompile` — Verifiable Provenance via Zero-Knowledge Compilation (2026)

- **Статус:** не прочитана (найдена 2026-06-28); прямой соседний путь — читать самому
- **Механизм:** компилятор исполняется внутри zkVM, на выходе — бинарник + криптодоказательство, что компиляция выполнена над заявленным исходником заявленным компилятором. Устойчив к подмене компилятора, тамперингу исходника, манипуляции выходом, replay.
- **Чего НЕТ (vs наш подход):** не атрибутирует входы (откуда каждый файл, какой RPM/коммит) — доказывает лишь корректность одной компиляции; огромный overhead zkVM; не работает с многошаговой реальной сборкой пакета as-is.
- **Для нас:** свежайший конкурирующий путь к доверенной сборке — пара к `attestable2025-tee` (TEE) и `lamb2021-reproducible`; контраст «криптодоказательство компиляции vs наблюдение фактической сборки с атрибуцией».

### `malka2026-lila` — Lila: Decentralized Build Reproducibility Monitoring (2026)

- **Статус:** не прочитана (найдена 2026-06-28)
- **Механизм:** децентрализованная оценка воспроизводимости для функциональной (Nix-подобной) модели пакетов: распределённый сбор результатов пересборки в общую БД, проверка совпадения независимо собранных бинарников.
- **Для нас:** инфраструктурный взгляд на reproducible builds в масштабе; контраст — нам не нужна вторая независимая сборка, мы атрибутируем единственную.

### `drexel2025-archverifier` — Independent Verifier for Arch Linux (2025)

- **Статус:** не прочитана (найдена 2026-06-28)
- **Суть:** развёрнут rebuilder/verifier для пакетов Arch Linux; найдена невоспроизводимость в 16 certbot-пакетах и в fwupd. Вывод: reproducible+bootstrappable builds + независимый аудит исходников снижают supply-chain-риски.
- **Для нас:** свежая эмпирика «воспроизводимость на практике трудна» (усиливает контраст `lamb2021-reproducible`); конкретные кейсы невоспроизводимости — материал для введения.

### `dietrich2026-mavenrebuild` — Variability of Source Code in Maven Rebuilds (2026)

- **Статус:** не прочитана (найдена 2026-06-28)
- **Суть:** совпадают ли исходники при независимой пересборке Java-пакетов Maven Central (Google Assured OSS, Oracle Build-from-Source). Главная причина расхождений — build-extensions, генерирующие код во время сборки.
- **Для нас:** довод, что «тот же исходник» нетривиально даже до бинарной воспроизводимости; сгенерированный на лету код наш трейсинг фиксирует фактически (реальные входы компилятора), а декларативный SBOM его пропускает.

## Патенты

### `patent2024-12164911` — Monitoring and auditing secure software builds (IBM)

- **Статус:** прочитан по Google Patents (2026-06-09)
- **Механизм:** НЕ syscall-трассировка как таковая, а адаптивный monitoring level per build instruction: indicator value → «глубина trace activities» → изменение детализации логирования; hardcoded mapping table (claim 9). Trace activities: сеть, сообщения, данные процессов, подпрограммы, CLI-ввод. Анализ: permitted/unpermitted списки инструкций; enforcement mode (убить сборку) или warning.
- **Патентный риск:** нет. Все независимые claims (1, 11, 12) требуют indicator value + изменение уровня логирования; у нас единообразная полная запись без уровней.
- **Чего НЕТ:** хэширования содержимого файлов, атрибуции происхождения.
- **Для статьи:** пример industrial policy-based build monitoring (IBM решает «много логов → детект», мы — «чьи это байты»); контраст выборочного логирования с полной записью.

### `patent2024-12067122` — Detecting added functionality in open source package (Microsoft)

- **Статус:** прочитан полностью, включая все 15 claims (2026-06-09, OCR скана); перевод формулы и анализ: [translations/patent2024-12067122.ru.md](translations/patent2024-12067122.ru.md); PDF: `pdf/patent2024-12067122.pdf`
- **Реквизиты:** Microsoft Technology Licensing (Shaver, De Castro, Shanmugam, Mazor); подача 2020-12-22, выдача 2024-08-20.
- **Механизм:** «пересобери и сравни» (приватизированная вариация reproducible builds): найти репозиторий исходников → пересобрать пакет в hardened-среде с параметрами исходной сборки → сравнить с опубликованным пакетом (побитово без подписей, затем по файловой структуре) → alert при расхождении. Независимые claims: 1 (система, интерпретируемый код), 7 (способ), 15 (система, машинный код + извлечение метаданных компилятора).
- **Патентный риск:** **нулевой** — все независимые claims требуют пересборки пакета и функционального сравнения пересобранного с исходным; в нашем методе этих шагов нет (наблюдаем единственную реальную сборку, атрибутируем входы хэшами).
- **Чего НЕТ (vs наш подход):** атрибуции происхождения (метод бинарный «совпало/нет», не скажет, откуда расходящийся файл); устойчивости к недетерминизму сборки (их «оценка согласованности различий» — эвристика); сравнение файловых структур обходится вредоносом с теми же именами/размерами.
- **Их сильная сторона:** применим post-hoc к уже опубликованному пакету; наша трассировка требует присутствия при сборке. Подходы комплементарны.
- **Для статьи:** контраст «rebuild & compare (требует воспроизводимости — исключена из SLSA 1.0) vs наблюдение фактической сборки». В их prior art цитируется OSSPolice (`duan2017-osspolice`).
