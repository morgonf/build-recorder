# Точная верификация сборочных зависимостей через ptrace и сравнение git-blob хешей

## Аннотация

Современные инструменты генерации SBOM для C/C++ проектов опираются на объявленные зависимости
(Cargo.lock, go.sum, conanfile.txt) или статический анализ исходного кода. Оба подхода
принципиально неточны: они не учитывают условную компиляцию, мёртвый код и вендорированные
зависимости без метаданных. Мы представляем систему на основе ptrace, которая отслеживает каждое
обращение к файловой системе в ходе реальной сборки, атрибутирует каждый файл к RPM-пакету по
хешу и верифицирует вендорированный код сравнением git-blob SHA-1 с историей upstream-репозитория.
Метод точно определил конкретный коммит вендорированной wslay в проекте aria2 как пост-релизный
снимок от 2022-08-25 — несмотря на то что configure.ac декларировал версию «1.1.1».

---

## 1. Введение

Вендоринг сторонних библиотек в C/C++ проектах (копирование исходного кода в `third_party/`,
`deps/`, `vendor/`) является распространённой практикой, создающей серьёзные проблемы для
аудита безопасности. В отличие от экосистем с централизованными менеджерами пакетов (npm, pip,
cargo), вендорированный C/C++ код не имеет машиночитаемых метаданных о версии и происхождении.

Существующие подходы к идентификации версий вендорированных зависимостей:

- **Строки версий в исходниках** (`#define WSLAY_VERSION "1.1.1"`, `AC_INIT([wslay], [1.1.1])`) —
  часто не обновляются после релиза при продолжении разработки
- **Имена директорий** (`lua-5.3.6/`, `duktape-1.8.0/`) — работают только при наличии версии в пути
- **OSV determineversion API** — отправляет хеши файлов в Google OSV для nearest-neighbor поиска;
  экспериментальный, не покрывает все библиотеки
- **CVE Binary Tool** (Intel/OSSF) — сканирует строки в скомпилированных бинарях; LTO устраняет
  большинство версионных строк

**Ключевая проблема:** ни один из этих методов не использует то, что уже содержится в каждом
git-репозитории — криптографически верифицированные хеши (blob SHA-1) каждой версии каждого файла.

---

## 2. Подход

### 2.1 build-recorder: ptrace-трассировка сборки

Система перехватывает системные вызовы (`open`, `openat`, `read`, `execve`, `rename`) посредством
`ptrace(PTRACE_SYSCALL)` и для каждого прочитанного файла вычисляет git-compatible SHA-1:

```
sha1("blob " + size + "\0" + content)
```

Результат — граф в формате RDF Turtle: процессы, файлы, отношения `b:reads`, `b:writes`,
`b:executable`, `b:creates`, `b:rename`.

**Ключевое преимущество перед статическим анализом:** git хранит blob объекты в том же формате.
Хеш файла из build-recorder можно напрямую сравнить с хешем в `git ls-tree` без перевычисления.

### 2.2 Атрибуция к RPM-пакетам (enrich.py)

После сборки RPM-база контейнера экспортируется:
```bash
rpm -qa --qf '[%{FILENAMES}\t%{NAME}\t%{NEVRA}\n]' > rpm-dump.txt
```

Каждый файл из графа сборки сопоставляется с предоставившим его пакетом. Критический нюанс:
в современных Linux-системах `/lib64/` является симлинком на `/usr/lib64/`, RPM хранит
канонический путь (`/lib64/libssl.so.3`), build-recorder записывает разрешённый
(`/usr/lib64/libssl.so.3`). Решение: индексирование обоих вариантов при загрузке rpm-dump.

### 2.3 verify-build.py: разделение статических и динамических зависимостей

Парсер плоского Turtle-формата строит граф процессов, классифицируя их как:
- **compiler** (cc1, cc1plus, gcc, g++) — читает заголовки и исходники
- **linker** (ld, collect2) — читает `.so` и `.a`; пишет финальные артефакты
- **assembler**, **archiver** — промежуточные шаги

Это позволяет точно разделить:
- **Статические зависимости** — заголовки и архивы, читаемые компилятором; атрибутированы к
  RPM-пакетам или помечены как вендорированные (нет RPM-провенанса)
- **Динамические зависимости** — `.so`, читаемые линкером; каждая с SHA-1 и NEVRA пакета
- **Артефакты** — файлы, созданные/переименованные линкером; отфильтрованы gcc temp-файлы

### 2.4 Upstream-верификация: точный коммит через сравнение хешей

Для каждой вендорированной директории:

1. Определяется соответствующий upstream-репозиторий (UPSTREAM_DB)
2. Клонируется bare-репозиторий (`~/.cache/build-recorder/repos/`)
3. Для каждого коммита в истории (от нового к старому): `git ls-tree -r COMMIT`
   сравнивается с хешами из build-recorder
4. Находится коммит с максимальным числом совпадений; при 100% — поиск останавливается
5. Определяется ближайший тег и расстояние до него

## 3. Результаты

### 3.1 civetweb 1.16-alt5 (SRPM)

| Категория | Файлы | Статус |
|---|---|---|
| Статика из RPM (заголовки + архивы) | 393 | ✓ верифицировано |
| Собственный код проекта | 64 | · |
| **Вендорированные источники** | **8** | **⚠ нет RPM-провенанса** |
| Динамические (.so) из RPM | 20 | ✓ верифицировано |

Вендорированные компоненты: `sqlite3.c`, `lfs.c`, `lsqlite3.c`, `LuaXML_lib.c` — все в
`src/third_party/`. Каждый файл имеет SHA-1 для ручной верификации с upstream.

### 3.2 aria2 (HEAD): обнаружение ошибки версионирования

aria2 вендорирует wslay WebSocket library в `deps/wslay/`. Идентификация по configure.ac
возвращает версию `1.1.1`. Upstream-верификация:

```
Comparing 9 key files against upstream (https://github.com/tatsuhiro-t/wslay.git):
  lib/wslay_event.c : build=4c29fe40  upstream-1.1.1=140f7c01  ✗ DIFFERS
  lib/wslay_frame.c : build=fa065eea  upstream-1.1.1=445e750c  ✗ DIFFERS
  lib/wslay_net.h   : build=23108701  upstream-1.1.1=23108701  ✓ MATCH
  ...
Result: 1/9 files match release-1.1.1 (11%)

Best match: commit 0e7d106ff89a (2022-08-25) — 100% confidence
Nearest tag: release-1.1.1 (+28 commits post-release)
```

**Вывод:** код wslay в aria2 — это снимок от 2022-08-25, на 28 коммитов новее последнего
релиза 1.1.1 (2020-06-20). Версионная строка в configure.ac никогда не обновлялась, поскольку
проект не выпускал формальных релизов с 2020 года.

Такой снимок включает рефакторинг внутренней очереди, исправления предупреждений clang-10
и другие изменения, отсутствующие в 1.1.1. Для CVE-мониторинга это означает неверный вектор
поиска уязвимостей: ни «wslay 1.1.1» ни «wslay 2022-08-25» не является корректным идентификатором
для запросов в NVD/OSV.

### 3.3 Envoy + Bazel

Контейнер расширен поддержкой Bazel (Bazelisk v1.29.0, Java 17, libcxx, lld). Для Envoy
потребовался Bazel 8.7.0 (из `.bazelversion`). Основное препятствие: `toolchains_llvm` не
поддерживает ALT Linux в списке известных дистрибутивов. Сборка без `--config=libc++` (с
системным toolchain) находится в процессе.

## 4. Сравнение с близкими подходами

### Bomfather (arXiv:2503.02097, март 2025)

Наиболее близкая система — Bomfather использует eBPF вместо ptrace для захвата обращений к
файловой системе и строит Merkle-деревья зависимостей. Ключевые различия:

| Аспект | build-recorder (ptrace) | Bomfather (eBPF) |
|---|---|---|
| Ядро Linux | 4.x+ | 5.8+ (BTF required) |
| Права | Обычный пользователь | Root или CAP_BPF |
| Формат вывода | RDF Turtle | Merkle tree + JSON |
| RPM атрибуция | ✓ (enrich.py) | — |
| Upstream verification | ✓ (git-blob) | — |
| Баз данных зависимостей | ✓ (UPSTREAM_DB) | — |
| Накладные расходы | ~15% | ~5% |

Bomfather фокусируется на полноте захвата (включая динамически загружаемые плагины), тогда как
наш подход — на атрибуции провенанса и точной верификации вендорированного кода.

### build-observer (GitHub: sbom-observer/build-observer)

Аналогичный инструмент наблюдения за файловыми операциями сборки. Не реализует RPM-атрибуцию
и upstream git-верификацию.

### OSV determineversion API

Google предлагает API, принимающий список `{path: sha1}` и возвращающий ближайший upstream-
коммит. Ограничения: экспериментальный статус, ожидает plain SHA-1 (не git-blob формат),
не покрывает всех проектов. Наш подход реализует аналогичную логику локально с полным
контролем над точностью.

## 5. Ограничения

1. **Git-blob vs plain SHA-1**: build-recorder вычисляет git-compatible хеши, OSV API ожидает
   plain SHA-1. При использовании `--source-dir` пересчёт хешей выполняется автоматически.

2. **Покрытие UPSTREAM_DB**: базе требуется ручное добавление для каждого нового компонента.
   Для неизвестных библиотек возвращается «нет записи в базе».

3. **Bazel + специфичные дистрибутивы**: `toolchains_llvm` поддерживает ограниченный список
   Linux-дистрибутивов. ALT Linux требует Ubuntu-совместимого base image или патча `toolchains_llvm`.

4. **LTO**: Link-Time Optimization устраняет версионные строки из скомпилированных бинарей
   (подтверждено на civetweb: LuaFileSystem, SQLite не имеют строк в .so). Решение — двухуровневый
   анализ: source SBOM + binary scan.

---

## 6. Заключение

Предложенный подход демонстрирует, что git-blob SHA-1 является оптимальным идентификатором
для вендорированного C/C++ кода: он криптографически верифицируем, уже вычислен git и
хранится в upstream-репозитории. Сравнение хешей 9 ключевых файлов wslay потребовало клонирования
репозитория (1.2 МБ) и прохода по 80 коммитам (<2 секунды) и дало детерминированный ответ,
недостижимый никаким методом статического анализа метаданных.

Практический вывод: для проектов вида aria2 (авторитетная система с вендорированными зависимостями
без формальных релизов) единственным надёжным способом идентификации является сравнение хешей
файлов, а не анализ строк версий.

Исходный код: https://github.com/[build-recorder-repo]  
Ветка с инструментами: `feature/verify-build`
