# Бэклог — идеи для тикетов фаз 4–6 и кросс-задачи

> Родительский документ: `doc/architecture-universal-provenance.md`.
> Это **не готовые тикеты**, а посевной материал: цель, идеи, открытые вопросы,
> скелет будущих тикетов. Оформлять в формат фаз 0–3 (`tickets-phaseN.md`) по
> мере подхода к фазе — через универсальный промт (`doc/sonnet-implementation-prompt.md`).
>
> Предусловие для всех: завершены фазы 0–2 (IR, classify, resolver, бэкенды),

## Фаза 4 — Языки и дистрибутивы (инкрементально)

**Цель.** Расширить охват: (а) объявленные зависимости через манифесты/lockfiles
для разных языков → `DepClass.DECLARED`; (б) атрибуция к пакету для не-RPM
дистрибутивов через новые `ProvenanceBackend`.

### Идеи тикетов

- **T4.1 ManifestParser API + Python.** `brec/manifests/base.py` (интерфейс из
  архитектуры §5.2) + `python.py`: `requirements.txt`, `poetry.lock`,
  `Pipfile.lock`, `*.dist-info/RECORD`, `pip`-метаданные. Источник — **только
  манифесты, реально прочитанные в графе** (исключает мёртвые).
- **T4.2 Node.** `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml` → purl `pkg:npm/...`.
- **T4.3 Go.** `go.mod`/`go.sum` → purl `pkg:golang/...`; учесть vendor/ режим.
- **T4.4 Rust.** `Cargo.lock` → purl `pkg:cargo/...`.
- **T4.5 dpkg backend.** `brec/provenance/dpkg.py`: `dpkg-query -S` /
  парсинг `/var/lib/dpkg/info/*.list`; deb-version; purl `pkg:deb/...`.
  Регистрация в `registry.py`; `available()` по наличию dpkg-БД.
- **T4.6 apk backend (Alpine).** `/lib/apk/db/installed`; purl `pkg:apk/...`.

### Открытые вопросы
- Связь DECLARED-манифеста с реально прочитанными файлами установленного пакета
  (манифест объявляет, граф подтверждает использование) — как сшивать.
- Для интерпретируемых ЯП «сборка» = упаковка, а не компиляция; семантика
  перехвата иная (что считать «использованной» зависимостью).
- Нормализация ecosystem→PURL для каждого менеджера; единый словарь.

### Скелет тикета (как в фазах 0–3)
Зависит → контекст → объём (сигнатуры) → вне объёма → критерий приёмки
(фикстура реального проекта на язык/дистрибутив, эквивалентность ожидаемому
набору DECLARED/PackageRef) → файл тестов.

## Фаза 5 — Изменённый вендоринг (fuzzy)

**Цель.** Идентифицировать вендоринг, который разработчик **пропатчил** — частый
кейс, ломающий exact git-blob. Дать `(проект, версия, confidence<1, method="fuzzy")`.

### Идеи тикетов

- **T5.1 Fuzzy-бэкенд.** `brec/identify/fuzzy.py` (`requires_network` зависит от
  стратегии). Похожесть файлов: TLSH/ssdeep или winnowing-фингерпринты.
- **T5.2 Стратегия «якорь + уточнение».** Часто часть файлов директории
  **не изменена** (заголовки, лицензии). Exact-match по ним → обнаружить repo
  (через resolver фазы 2), затем fuzzy-сравнение **изменённых** файлов с
  историей этого repo → ближайший коммит + метка «modified (patched)».
- **T5.3 Метрики и пороги.** Доля exact vs fuzzy в компоненте; порог
  confidence; контроль ложных срабатываний; отражение в отчёте «N файлов
  пропатчено относительно upstream».

### Открытые вопросы
- Пороги похожести и борьба с false-positive.
- Производительность fuzzy-сравнения по длинной истории (кэш, ограничение глубины).
- Где брать корпус, если ни один файл не совпал exact (нет якоря) — деградация.

### Критерий приёмки (ориентир)
Искусственная фикстура: взять реальный upstream-файл, внести правки → бэкенд
определяет исходный проект/коммит с confidence в заданном диапазоне и метит
«modified».

## Фаза 6 — Заимствования-сниппеты

**Цель.** Детектировать **скопированные фрагменты** (функции/блоки) из известных
проектов внутри файлов, выглядящих как оригинальный код проекта (пример: Python-
заимствования). Самый трудный, research-grade уровень.

### Идеи тикетов

- **T6.1 Sub-file fingerprinting.** Winnowing (Moss-стиль) k-gram фингерпринты
  ИЛИ function-level: парс через tree-sitter → нормализация → хеш функций.
  `method="snippet"`, location-ranges, низкая confidence.
- **T6.2 Корпус/индекс.** Фингерпринт-индекс корпусов-кандидатов (популярные
  библиотеки по языкам) или запрос к внешнему сервису; язык-зависимый
  токенизатор/парсер (грамматики tree-sitter).
- **T6.3 Интеграция.** Сниппет-провенанс как отдельный раздел отчёта; не
  смешивать с файловым вендорингом.

### Открытые вопросы
- Масштаб корпуса и где его держать (локально vs сервис).
- Приватность (отправка фрагментов наружу — чувствительнее, чем хеши файлов).
- Производительность; язык-зависимость; нормализация (форматирование, имена).

### Критерий приёмки (ориентир)
Python-фикстура со скопированной функцией из известного проекта → детектируется
с указанием источника и диапазона строк.

## Кросс-задачи (вне линейной нумерации фаз)

Оформлять отдельными тикетами по приоритету; не блокируют фазы 0–3.

- **X.1 eBPF capture-бэкенд.** Альтернатива ptrace (ниже накладные расходы — см.
  сравнение с Bomfather в `doc/article-build-provenance.md`). Тот же формат
  `.out`; выбор бэкенда — флагом. Требует ядро 5.8+ / CAP_BPF.
- **X.2 CI-интеграция.** GitHub Actions / GitLab CI: запуск build-recorder как
  шага сборки, публикация `sbom.json` как артефакта; пример workflow.
- **X.3 Единый `brec/cli.py`.** Полная унификация подкоманд
  (`graph|classify|identify|vuln|analyze`) поверх стадий IR (архитектура §10).
- **X.4 Производительность на больших сборках.** Envoy/Bazel (часы, крупные
  `.out`): профилирование парсера и resolver, потоковая обработка, кэш-стратегии.
- **X.5 NVD как второй источник CVE + cve-bin-tool.** Перекрёстная проверка
  бинарного скана (LTO-устойчивость) — дополнение к OSV (фаза 3).
- **X.6 Переход записи на `b:pkg_*`.** Сменить enrich-сторону с `b:rpm_*` на
  обобщённые `b:pkg_*` (читатель уже совместим после T0.4); обновить схему и
  потребителей.

## Принципы при оформлении любого будущего тикета (памятка)

- Формат фаз 0–3: **зависит → контекст → объём (сигнатуры) → вне объёма →
  критерий приёмки → файл тестов**.
- Behavior-preserving там, где трогается существующий вывод (golden-тесты).
- Сетевое — на записанных ответах; кэш; деградация в офлайн.
- Никаких тяжёлых зависимостей без явного обоснования.
- Привязка к реальным именам в коде/схеме, не догадки.
- Универсальность как проверяемый критерий: ядро не знает про конкретный
  дистрибутив/язык/компонент — только через интерфейсы-плагины.
