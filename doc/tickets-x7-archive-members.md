# X.7. Члены статического архива, вошедшие в линковку

> Кросс-задача из `doc/backlog-phases-4-6.md`. Опыт, на котором держится тикет,
> и его воспроизведение лежат в `experiments/ar-members/` (README и `repro.sh`).

**Зависит от:** ничего (тракер и `brec verdict` в нынешнем виде)
**Размер:** M

### Контекст

Сейчас вердикт про статический архив целиковый. Если компоновщик прочитал
`libz.a`, не собранный в этой сборке, результат получает RED с указанием файла
и пакета-владельца (USAGE.md, раздел о предсобранных объектах). Какие члены
архива реально вошли в результат, неизвестно. Для SBOM и CVE это существенно.
«Из `libz.a` вошли `inflate.o`, `crc32.o`, `adler32.o`» это перечень кода в
результате, а «прочитан `libz.a`» только факт обращения. Уязвимая функция в
невключённом члене означает, что результат не затронут.

Опыт показал, что ответ уже лежит в системных вызовах. LTO-плагин gcc, который
драйвер подключает по умолчанию, вызывается на каждом загружаемом объекте и
читает ELF-заголовок члена коротким чтением ровно с первого байта его данных.
Для ld.bfd, ld.gold и cgo с внешней линковкой это дало ровно те члены, которые
указывает map-файл компоновщика. Признак не зависит от пакетного формата, он
появится в любой сборке, где линкует gcc (make, CMake, autotools, meson, rpm,
dpkg, Yocto, cgo).

Тракер останавливается на каждом системном вызове (`PTRACE_SYSCALL` без
seccomp-фильтра, `src/tracer.c`), поэтому учёт `read`, `lseek` и `pread64`
не добавляет остановок, только работу на выходе из вызова.

### Объём работ

1. **Тракер (`src/tracer.c`, `src/types.h`).**
   - При `open`/`openat`/`openat2` на чтение определять, архив ли это, по той же
     магии, что `get_file_kind()` в `src/hash.c` (`!<arch>\n`). Перед выбором
     способа проверить по коду, хешируются ли входы при закрытии. Если да,
     чтение 8 байт при открытии ничего не стоит на фоне хеша.
   - Для дескрипторов архивов вести позицию (результат `lseek`, сумма
     результатов `read`) и копить смещения коротких чтений (меньше 4096 байт) у
     `read` и `pread64`. Состояние наследуется через `dup`, `dup2`, `dup3`,
     `fcntl(F_DUPFD*)` тем же путём, каким тракер уже передаёт дескрипторы
     (коммит 817a8c1). Без этого второй член теряется (см. README опыта).
   - `mmap` дескриптора архива отмечать, потому что члены в этом случае по
     чтениям не видны.
   - При последнем закрытии, когда файл и так читается для хеша, разобрать
     таблицу членов ar (60-байтные заголовки, длинные имена через `//`) и
     отобразить накопленные смещения на начала данных членов.
2. **Запись (`src/record.c`, `doc/build-recorder-schema.ttl`).** Новый узел на
   каждый загруженный член и два предиката. Имена ниже предлагаемые, их можно
   сменить при реализации, если они расходятся с принятыми в схеме.
   ```turtle
   pN b:loads_member mK .
   mK b:member_of fM ; b:name "inflate.o" ; b:hash "<sha1 данных члена>" .
   ```
   Хеш данных члена позволяет сопоставить член с тем же объектом в другом
   архиве, пакете или в upstream-сборке.
3. **Честность при отсутствии признака.** Если члены не видны (плагин выключен,
   lld, mold), их не перечислять, а верхнюю границу по полным чтениям у bfd не
   выдавать за перечень. *(Изменено в прототипе 2026-10-25.)* Отдельной отметки
   тракер не пишет. Первоначальный план (`b:coverage_gap` с видом
   `archive-members`) не годится, потому что `verdict.py` превращает любой
   пробел покрытия в GREY, а файловый слой здесь полон. Отметка на стороне
   тракера (`b:members_unseen`) тоже не прижилась, потому что тракер не отличает
   компоновщик от `go tool compile`, читающего архивы пакетов Go (формат ar),
   и на сборке Go с cgo дал 331 ложную отметку. Вывод делает анализ по тому,
   что уже записано. Компоновщик прочитал архив и прочитал `liblto_plugin.so`,
   значит, перечень `b:loads_member` точен (возможно, пуст). Плагин не читал,
   значит, члены неизвестны.
4. **Анализ (`brec/ir.py`, `brec/commands/verdict.py`).** Читать новые тройки.
   В строке RED для архива перечислять загруженные члены с хешами, в JSON
   вывода отдельным полем. Цвет вердикта не меняется. Архив, не собранный здесь,
   остаётся RED независимо от числа членов. При пробеле покрытия писать
   «члены не определены» вместо пустого списка.

### Вне объёма

- lld, mold и другие компоновщики, которые мапят входы. По ptrace это не
  видно. Путь через подстановку `-Wl,-Map` или `--why-extract` это отдельный
  тикет, потому что он вмешивается в сборку.
- Удаление секций через `--gc-sections`. Загруженный член это верхняя граница
  кода в результате, а не точное множество функций.
- Сопоставление члена с CVE на уровне функций и компонентная гранулярность в
  CycloneDX. Это следующий шаг поверх перечня членов.
- Тонкие архивы (`!<thin>`). Их члены отдельные файлы и уже видны через
  `openat`; проверить только, что поведение не сломалось.

### Критерий приёмки

1. Все пять случаев `experiments/ar-members/repro.sh`, записанные
   build-recorder вместо strace, дают в `.out` ровно `s6.o` и `s9.o` для bfd и
   gold с плагином и для cgo. Для двух случаев без плагина записан пробел
   покрытия, а членов нет.
2. Положительный контроль из USAGE.md (upstream civetweb v1.16, статический
   `libz.a` из `zlib1g-dev`): RED по `libz.a` перечисляет члены, и перечень
   совпадает с секцией «Archive member included» map-файла той же линковки
   (`LC_ALL=C`, `-Wl,-Map`).
3. Одна rpm-сборка в hasher со статической линковкой системного `.a`: тот же
   критерий совпадения с map-файлом.
4. Замер на `benchmark/` до и после. Порог не задаётся, цифры идут в отчёт
   тикета; заметный рост считается дефектом, который надо объяснить.

### Файлы тестов

- `tests/collect-smoke.sh`: случай с архивом из нескольких членов и проверкой
  перечня по `.out`.
- `tests/test_provenance_verdict.py`: фикстура `.out` с тройками членов и
  с компоновщиком без плагина, проверка текста и JSON вердикта.

### Прототип (2026-10-25)

Сделаны пункты 1 и 2 и изменённый пункт 3, пункт 4 (анализ) не начат.

- **Тракер.** При открытии на чтение файл с магией `!<arch>\n` разбирается
  один раз на узел содержимого (`ar_parse`, длинные имена GNU через `//` и
  имена BSD `#1/`). Его дескрипторы ведутся в отдельной таблице процесса, с
  общим смещением у копий `dup*` и `fcntl(F_DUPFD*)`. Короткое (меньше 4096
  байт) чтение `read` или `pread64` ровно с начала члена пишет член, но только
  если этот образ процесса открыл `liblto_plugin.so`. Признак плагина
  сбрасывается на `execve`. Дескрипторы, открытые на чтение, основная таблица
  тракера не ведёт (файл хешируется при открытии), поэтому таблица отдельная.
- **Запись.**
  ```turtle
  :m0  a b:member ; b:member_of :f21 ; b:name "zutil.o" ; b:hash "<git-blob>" .
  :p2  b:loads_member :m0 .
  ```
  Узел члена пишется один раз, хеш считается по байтам члена так же, как у
  извлечённого объекта.
- **Схема.** `b:member`, `b:member_of`, `b:loads_member` в
  `doc/build-recorder-schema.ttl`.
- **configure.ac.** Проверки `SYS_read`, `SYS_pread64`, `SYS_lseek`.
