# Универсальный промт для реализации тикета (Sonnet)

> Назначение: единый промт, который ставит модели Sonnet задачу реализовать
> **один тикет** из фаз проекта build-recorder, соблюдая все сквозные правила.
> Параметры — в блоке «ВХОДНЫЕ ДАННЫЕ»: заполнить и отправить.
>
> Использование: открыть сессию в корне репозитория `build-recorder`, вставить
> промт ниже, заполнив `{{...}}`. Один тикет = одна сессия = один PR.

---

## Промт (копировать целиком, заполнив поля)

```
Ты реализуешь ОДИН тикет в проекте build-recorder. Работай строго в рамках его
scope. Не делай работу из других тикетов/фаз.

ВХОДНЫЕ ДАННЫЕ
- Тикет: {{например, T2.3}}
- Файл тикета: {{например, doc/tickets-phase2.md}}
- Рабочая директория: корень репозитория build-recorder.

ШАГ 0 — КОНТЕКСТ (прочитать перед кодом, ничего не меняя)
1. Прочитай архитектуру: doc/architecture-universal-provenance.md — разделы,
   на которые ссылается тикет (модель данных §3, интерфейсы §5, стадии §6–§9).
2. Прочитай файл тикета целиком и найди свой тикет: его «Объём работ»,
   «Вне объёма», «Критерий приёмки», «файл тестов», «Зависит от».
3. Прочитай ВСЕ существующие файлы кода, на которые ссылается тикет (например
   enrich.py, sbom.py, verify-build.py, brec/*). Привязывайся к РЕАЛЬНЫМ именам
   предикатов RDF, полей, функций и множеств — не выдумывай. Имена предикатов —
   из doc/build-recorder-schema.ttl.
4. Если тикет «Зависит от» предыдущих — убедись, что их артефакты на месте
   (модули/структуры существуют). Если нет — СТОП, сообщи, не реализуй зависимости.

ШАГ 1 — ПЛАН
Кратко изложи: какие файлы создашь/изменишь, какие сигнатуры, какие тесты и
какие фикстуры нужны. Сверь план с «Критерием приёмки» тикета — каждый пункт
приёмки должен быть покрыт тестом.

ШАГ 2 — GOLDEN BASELINE (только если тикет behavior-preserving)
Если тикет меняет существующий скрипт (enrich.py/verify-build.py/sbom.py) и
требует «вывод не изменился»: СНАЧАЛА зафиксируй эталонный вывод ДО правок
(запусти на доступных фикстурах, сохрани в tests/golden/). Задокументируй
нормализацию недетерминированных полей (timestamps и т.п.).

ШАГ 3 — РЕАЛИЗАЦИЯ
- Только scope тикета. Ничего из «Вне объёма».
- Python 3.11+, тип-аннотации в стиле существующего кода.
- БЕЗ тяжёлых зависимостей (без rdflib для парсинга и т.п.), если тикет явно не
  разрешает. Парсер .out — ручной, как в существующих скриптах.
- Ядро (brec/classify.py, brec/cli.py, resolver) НЕ импортирует distro-/язык-/
  компонент-специфику напрямую — только через интерфейсы-плагины
  (ProvenanceBackend / ManifestParser / IdentificationBackend).
- Сетевые бэкенды: кэш ответов на диск, бэкофф на 429, тихая деградация при
  отсутствии сети (не падать — помечать причину). НИКОГДА не выдумывать данные
  (версии, CVE, совпадения) — при незнании возвращать пусто + пометку.
- Стиль: следуй окружающему коду (нейминг, плотность комментариев, идиомы).

ШАГ 4 — ТЕСТЫ
- Напиши тесты в указанный тикетом файл (tests/test_*.py).
- Каждый пункт «Критерия приёмки» → конкретный тест.
- Сетевое тестируй на ЗАПИСАННЫХ ответах (локальные JSON-фикстуры / VCR-стиль):
  тесты должны проходить ОФЛАЙН и детерминированно.
- IR-структуры: round-trip тест (from_dict(to_dict(x)) == x; dump→load).
- Behavior-preserving: golden-тест (побайтовое совпадение с baseline из ШАГ 2,
  с задокументированной нормализацией).
- Запусти `pytest tests/` из корня. Все тесты — зелёные.

ШАГ 5 — САМОПРОВЕРКА И ОТЧЁТ
Пройди по «Критерию приёмки» и «Definition of Done» — отметь каждый пункт фактом
(каким тестом покрыт). Проверь «Вне объёма» — ничего лишнего не реализовано.
Если что-то не удалось — честно сообщи, что и почему, не маскируй.
В финале дай: список изменённых/созданных файлов, как запускать тесты, и
краткое подтверждение каждого критерия приёмки.

ЗАПРЕТЫ
- Не коммить и не пуш без явной просьбы.
- Не менять формат вывода существующих команд, если тикет это не предписывает.
- Не расширять scope «заодно». Идеи для других тикетов — записать в конце отчёта,
  не реализовывать.
- Не вводить курируемую базу как обязательную часть ядра идентификации.
```

## Заметки по применению

- **Один тикет — одна сессия.** Контекст между тикетами передаётся через
  артефакты в репозитории (модули `brec/`, тесты, фикстуры), а не через память
  модели.
- **Порядок важен.** Соблюдай «Зависит от» и рекомендованный порядок внутри
  фазы (указан в шапке каждого `tickets-phaseN.md`).
- **Фикстуры — общий ресурс.** `tests/fixtures/` (tiny.out и пр.) и
  `tests/golden/` создаются в ранних тикетах и переиспользуются; не дублировать.
- **Если тикет крупный (L).** Можно разбить реализацию на под-шаги внутри одной
  сессии, но scope и приёмка — как в тикете; не выходить за «Вне объёма».
- **Ревью.** После зелёных тестов — прогнать `/code-review` по диффу перед PR
  (по желанию заказчика).
