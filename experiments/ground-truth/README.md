# Сверка трассы с эталоном: протокол и результаты

Вопрос, на который отвечает этот эксперимент: **можно ли проверить, что трасса
build-recorder действительно описывает состав сборки**, а не выглядит
правдоподобно. Проверять утверждение о наблюдении вторым наблюдением того же
рода бессмысленно, поэтому эталон берётся у инструмента с другим механизмом.

## Приборы

У каждого компилятора есть собственная бухгалтерия входов, которую он ведёт для
своих нужд и никак не согласует с ядром:

| Язык | Эталон | Механизм |
|------|--------|----------|
| C, C++ | `gcc -MD` | препроцессор перечисляет включённые заголовки |
| Rust | `rustc --emit=dep-info` (cargo пишет сам) | компилятор перечисляет прочитанные файлы |
| Go | `go version -m <binary>` | тулчейн вшивает список модулей в сам бинарь |
| Rust, Go | `Cargo.lock`, `vendor/modules.txt` | точный состав компонентов экосистемы |

Для C эталон приходится включать: на PATH подставляется обёртка
[`cc-wrapper.sh`](cc-wrapper.sh), дописывающая `-MD -MF` к каждой компиляции.
Обёртка не трогает препроцессирование, линковку и вызовы, где `-M`-флаг уже
задан, и рядом с каждым депфайлом кладёт рабочий каталог: депфайл называет входы
так, как их написали в команде, поэтому относительные имена без каталога
бессмысленны.

## Критерий приёмки

Пусть R это множество из эталона, T это множество из трассы.

- **R \ T обязано быть пустым.** Компилятор записал, что читал файл, а
  трассировщик его не увидел: это дефект трассировщика, и одна такая запись
  стоит больше, чем любое число чистых прогонов.
- **T \ R пустым быть не должно.** Депфайл покрывает только препроцессирование,
  поэтому сам компилятор, его specs, `crt*.o`, библиотеки, входы линковки и всё
  сгенерированное на лету в него не попадают по построению. Требование к этой
  разнице другое: она должна раскладываться по объяснимым категориям.

На уровне компонентов вопросов два, и интереснее второй: видит ли трасса всё,
что тулчейн считает использованным, и какие завендоренные компоненты сборка не
трогала вовсе. Второе превращает тезис «трасса исключает несобиравшееся» из
анекдота в число.

## Как запустить

```bash
docker build -t build-recorder:latest -f docker/Dockerfile .
docker build -t build-recorder:ground-truth -f experiments/ground-truth/Dockerfile .

docker run --rm --cap-add=SYS_PTRACE --security-opt seccomp:unconfined \
  -v ~/srpms:/srpms:ro -v ~/build-recorder-out/gt/zlib:/output \
  build-recorder:ground-truth /srpms/zlib-1.3.1-alt1.src.rpm

python3 experiments/ground-truth/compare_files.py OUT/zlib-build.out \
  --depfiles OUT/depfiles --rpm-dump OUT/rpm-dump.txt

python3 experiments/ground-truth/compare_modules.py OUT/fd-build.out \
  --cargo-lock OUT/ground-truth/Cargo.lock --rust-depinfo OUT/rust-depinfo
```

Сборка идёт `rpmbuild --nodeps -bc`, то есть только `%prep` и `%build`. Чтобы
получить то, что реально уезжает в пакет, нужен ещё `%install`:

```bash
docker run --rm --cap-add=SYS_PTRACE --security-opt seccomp:unconfined \
  -e RPMBUILD_STAGE=-bi \
  -v ~/srpms:/srpms:ro -v ~/build-recorder-out/gt/fzf:/output \
  build-recorder:ground-truth /srpms/fzf-0.65.1-alt1.src.rpm

python3 -m brec verdict OUT/fzf-build.out --rpm-dump OUT/rpm-dump.txt \
    --payload OUT/payload
```

В этом режиме скрипт складывает buildroot в `OUT/payload/`, и вердикт можно
замкнуть по нему.

### Честная оговорка: трасса шире артефакта

`TOUCHED BUT NOT IN THE FINAL ARTIFACT`: у fd 37 крейтов, у fzf 5 модулей были
прочитаны при сборке, но в бинарь не попали (build-скрипты, dev-зависимости,
пробы, отброшенное компоновщиком). Значит трасса сама по себе даёт **верхнюю
оценку** состава артефакта, и утверждение «в артефакте ровно это» она без
дополнения не обосновывает. Замыкание даёт сверка с поставляемыми файлами
(`brec verdict --payload`), которая сопоставляет содержимое по хешу.

## Перепрогон на исправленном коде (2026-09-06)

Слой анализа с тех пор изменился: `parse_out` научился читать rename-рёбра и
перестал собирать граф в порядке множества, `b:executable` перестал теряться.
Прогон повторён на тех же трассах, теми же двумя инструментами.

**Файловый и компонентный уровни воспроизвелись полностью**, все числа таблиц
выше совпали до единицы: депфайлов 45/297/40, R = 126/1059/209, прочитано в
трассе 1146/6885/4304, R \ T = 0 везде, T \ R = 1020/5826/4095; крейты fd
95/57/0/1, модули fzf 11/6/0/0. Иначе и не могло быть: обе сверки опираются
только на рёбра чтения, а правки касались переименований, порядка узлов и
запусков.

Сдвинулся вердикт, и здесь перепрогон нашёл два дефекта.

**1. Вердикт не воспроизводился.** Пять прогонов `brec verdict` на одной и той
же трассе fd давали GREY 192, 197, 195, 195, 193. Причина в порядке обхода
множества (исправлено в `f8b193f`), а не в данных. Числа, полученные до этого
коммита, невоспроизводимы by construction, и любое из них было одним броском.

**2. Родословная обрывалась на цикле.** Файл, который записали, прочитали и
записали снова, лежит на собственной родословной. Обход останавливался на
повторном посещении и кэшировал этот обрыв, то есть отвечал «для этого пути
обхода», а не «для этого файла», после чего раздавал ответ всем последующим.
Циклы теперь сворачиваются в компоненты связности (алгоритм Тарьяна,
итеративный), и вопрос снимается: всё, что читает цикл, есть родословная
каждого файла в нём, с какой стороны ни заходи.

| Пакет | GREY до | GREY после | RED до | RED после |
|-------|---------|------------|--------|-----------|
| zlib | 196 | 196 | 0 | 0 |
| fd | 194 | **133** | 0 | 0 |
| fzf | 14 | 14 | 1249 | **1309** |

Сдвиг двусторонний, и это существенно: на fd 61 файл был GREY только потому,
что его родословную обрезали, а на fzf 60 файлов, наоборот, числились GREEN,
хотя их родословная через цикл приводит к бинарнику без происхождения. Обрыв
не просто шумел, он **прятал инкорпорацию прекомпилята**, то есть ошибался в
сторону, противоположную назначению инструмента. Время не выросло: 25 секунд
на трассе fd против 26 у прежнего обхода.

### Разбор RED у fzf: хеш снимается на close, а не на записи

1309 RED у fzf сводились к четырём листьям, все четыре это `_pkg_.a` в кэше
сборки Go. Разбор по трассе даёт полную картину для
`/tmp/go-build1370413324/b010/_pkg_.a`:

| Строка .out | Событие |
|---|---|
| 24013 | `:p74 b:writes :f3781` (открыт на запись, хеш ещё не снят) |
| 24085 | `:f3787 b:hash "075d6828…"` (хеш снят при открытии на чтение) |
| 24086 | `:p82 b:reads :f3787` |
| 24102 | `:p82 b:writes :f3789` |
| 24105 | `:f3789 b:hash "94224d6e…"` (снят на close p82) |
| 26349 | `:f3781 b:hash "94224d6e…"` (снят на close p74: содержимое, оставленное p82) |

`p74` и `p82` это два потока одного и того же `go build`: трассировщик видит
каждый поток отдельным процессом, а кэш сборки Go пишется несколькими рабочими
потоками. Хеш узла, открытого на запись, снимается в `close()`
(`src/tracer.c:634`), то есть описывает содержимое пути на момент закрытия, а не
то, что записал этот процесс. Пока `p74` держал дескриптор открытым, `p82`
перезаписал файл, и на close `p74` получил чужое содержимое.

Промежуточное состояние `075d6828`, которое реально прочитал `p82`, в итоге не
принадлежит ни одному узлу записи. Именно этот осиротевший узел приходил в
вердикт как «бинарник без происхождения», и RED расползался по всему, что от
него зависит. Узлов такого вида (файл по пути, куда сборка писала, но без
собственной записи) в трассах: fzf 43, fd 390, zlib 124.

Это дефект не наблюдения, а атрибуции: событие записи трассировщик видел, но
приписал ему не то содержимое. Устранить его полностью на уровне трассировщика
нельзя без хеширования при каждой записи (и при конкурентных потоках даже это
не даёт однозначной привязки), поэтому вердикт разведён на два случая:

- бинарник без OS-пакета **по пути, куда сборка не писала** остаётся RED, это
  прежний «чужой прекомпилят»;
- бинарник без OS-пакета **по пути, куда сборка писала**, но не произведённый
  ни одной наблюдённой записью, теперь GREY со своей формулировкой и списком
  `← unattributed`.

Гарантия от этого не слабеет: GREY не даёт GREEN, то есть пакет по-прежнему не
может быть объявлен собранным из исходников. Меняется только обвинение: сказать
«инкорпорирован чужой прекомпилят» о промежуточном состоянии собственного файла
сборки было неверно.

| Пакет | RED до разбора | RED после | GREY после |
|-------|----------------|-----------|------------|
| fzf | 1309 | **0** | 1323 |
| fd | 0 | 0 | 133 |
| zlib | 0 | 0 | 196 |

Вердикт fzf становится GREY вместо RED. Фиделити 18.8% как была, так и
осталась: она считает долю GREEN, а эти файлы GREEN и не были.

### /dev/null числился артефактом сборки

Разбор GREY после двух правок выше показал, из чего он состоит, и ответ оказался
не про сборки. У zlib все 196 GREY это `/dev/null`, по узлу на каждое открытие.
Записанных узлов `/dev/null` в трассах: zlib 489, fd 1115, fzf 160, и каждый
проходил как артефакт: имя без расширения, а правило «файл без расширения это
собранный исполняемый» ловит и его. Из 846 «артефактов» zlib 489 были
`/dev/null`, то есть **больше половины знаменателя фиделити**.

Запись в `/dev/null`, `/proc` и `/sys` ничего не производит: это не файлы
сборки, у них нет ни родословной, ни вердикта. Теперь такие пути исключены и из
произведённого, и из артефактов. `/dev/shm` намеренно оставлен обычным
хранилищем: прекомпилят, положенный туда, инструмент обязан видеть.

Числа менялись в обе стороны, и обе показательны: у zlib исчез весь GREY,
у fzf упала фиделити, потому что раньше 160 узлов `/dev/null` считались
успешными артефактами и завышали долю GREEN.

### Итоговые числа вердикта (2026-09-06)

| Пакет | Вердикт | Произведено | Артефактов | GREEN | RED | GREY | Фиделити |
|-------|---------|-------------|------------|-------|-----|------|----------|
| zlib | 🟢 GREEN | 1621 | 357 | 1621 | 0 | 0 | 100% |
| fd | ⚪ GREY | 8046 | 1108 | 7965 | 0 | 81 | 100% |
| fzf | ⚪ GREY | 2388 | 1150 | 1081 | 0 | 1307 | 8.9% |

До перепрогона те же трассы давали zlib 76.8% с 196 GREY, fd 97.7%, fzf RED с
18.9%. Ни одно из этих чисел не было воспроизводимым, и все три были искажены
`/dev/null` в знаменателе.

zlib GREEN означает ровно то, что написано в критерии: каждый произведённый файл
сводится к исходному тексту и файлам OS-пакетов. Утверждения о поставляемом
пакете это ещё не даёт, для него нужен `--payload`.

Оставшийся GREY: у fd это 81 `.o`, чьи процессы-производители не показали
чтений; у fzf 1307 файлов, упирающихся в разрыв атрибуции из предыдущего
раздела. Первое пока не разобрано, второе требует хеширования при открытии на
запись.

## Перезапись эталона на исправленном трассировщике (2026-09-06)

Разбор оставшегося GREY у fd (81 файл, все `*.rcgu.o`) вывел на дефект самого
трассировщика: `pthread_create` в современной glibc идёт через `clone3`, а среди
перехватываемых были только `fork`, `vfork` и `clone`. Поток приходил как
трассируемый без родителя и получал собственный субъект, поэтому у rustc чтение
крейта оказывалось у одного узла, а запись объекта у другого, без связи между
ними. Через `clone3` в той же glibc идёт и обычный `fork`, отчего у zlib 155
узлов из 2997 тоже висели без родителя.

Исправлено двумя частями: перехват `clone3` и, главное, свёртка потоков в
процесс. Поток делит адресное пространство и таблицу дескрипторов с лидером
группы, отдельным процессом не является, и всё, что он делает, записывается под
субъектом лидера (`Tgid` из `/proc/<tid>/status`, ребро `creates` для потока не
пишется, `end` лидера потоком не закрывается). Воспроизводитель на 60 строк
лежит в `examples/threads.c` и проверяется в CI.

Три пакета пересобраны и перезаписаны этим трассировщиком:

| Пакет | Процессов | Без родителя | GREY | Вердикт | Фиделити |
|-------|-----------|--------------|------|---------|----------|
| zlib | 2997 → 2996 | 155 → **1** | 0 → 0 | GREEN → GREEN | 100% |
| fd | 5916 → **5373** | 1286 → **5** | 81 → **0** | GREY → 🟢 **GREEN** | 100% |
| fzf | 1507 → **506** | 34 → **1** | 1307 → 1479 | GREY → GREY | 8.9% → **2.2%** |

Сверка с эталоном на новых трассах прошла в тех же числах: депфайлов 45/297/40,
R = 126/1059/209, прочитано 1146/6885/4304, **R \ T = 0 во всех трёх**, крейты
fd 95/57/0/1, модули fzf 11/6/0/0. То есть свёртка потоков не потеряла ни одного
чтения, зафиксированного компилятором.

fd стал GREEN: 81 объект, висевший без родословной, теперь связан с чтениями
своих же потоков.

У fzf число ухудшилось, и это честно: граф стал связнее, поэтому осиротевшие
узлы кэша Go (разрыв атрибуции close-хеша, предыдущий раздел) достают теперь до
большего числа файлов. Пока хеш снимается на `close()`, оценка Go-сборки этим
инструментом упирается в 2.2%, и это оценка инструмента, а не сборки.

## Фиделити по поставляемому, а не по всему наблюдённому (2026-09-06)

Число 2.2% для fzf оказалось артефактом знаменателя. Разбор 1479 серых файлов
показал, где они лежат:

| Где | Сколько | Уезжает в пакет? |
|-----|---------|------------------|
| `/root/.cache/go-build` | 757 | нет |
| `/tmp/go-build*` | 467 | нет |
| `/root/.config/go` | 173 | нет |
| `/output/depfiles` (депфайлы обёртки `cc` из этого же эксперимента) | 21 | нет, это прибор |
| прочее временное | ~59 | нет |
| `bin/` дерева сборки | **2** | да |

То есть метрика считалась по внутреннему кэшу Go. Модель угроз с самого начала
говорит, что без `--payload` вердикт не является утверждением о пакете; здесь
это видно в цифрах.

Сборки повторены с `%install` (`RPMBUILD_STAGE=-bi`), buildroot сохранён, вердикт
замкнут по нему:

| Пакет | Поставляется файлов | GREEN | RED | GREY | Фиделити по payload |
|-------|---------------------|-------|-----|------|---------------------|
| zlib | 88 (+12 симлинков) | 75 | **0** | 13 | **85.2%** |
| fd | 532 (+2 симлинка) | 524 | **0** | 8 | **98.5%** |
| fzf | 14 | 12 | **0** | 2 | **85.7%** |

Ни одного RED ни в одном пакете: инкорпорации чужих прекомпилятов в том, что
уезжает, не найдено.

Из чего состоит оставшийся GREY поставляемых файлов:

- **rpm-обвязка**: `.findpackage-commands`, `.tmp/files`, `.debuginfo/links/…`,
  `.debuginfo/src/…`. Это служебные файлы сборочной системы, а не выход
  компилятора;
- **файлы, поставленные как есть** (у zlib 5, у fd 6): «содержимое совпадает с
  файлом, который сборка только читала». Скрипты и заголовки, положенные
  `install` без изменений. Провенанс у них как раз хороший, помечены они так
  потому, что записи в buildroot трассировщик не увидел;
- **`usr/bin/fzf`**: тот самый разрыв атрибуции close-хеша в кэше Go.

Из 634 поставляемых файлов трёх пакетов не подтверждён ровно 1 бинарник, и
причина известна поимённо.

## Что эксперимент нашёл в самом build-recorder

Сверка окупилась ещё до сравнения множеств: до неё Rust и Go не трассировались
вовсе, а на C терялась треть графа.

1. **Гонка с умирающим потоком, дважды.** `PTRACE_GET_SYSCALL_INFO` и перезапуск
   `PTRACE_SYSCALL` возвращают `ESRCH`, когда трассируемый умер между сообщением
   `wait(2)` и обращением к нему. Обе ситуации были фатальными и убивали трассу
   целиком: сборка Go не доходила до конца ни разу. Теперь это пропуск события.
2. **`mmap` работает не на всём, что читается.** Файлы sysfs и procfs сообщают
   размер, но страниц за ними нет; рантайм Go читает
   `/sys/kernel/mm/transparent_hugepage/hpage_pmd_size` при каждом старте.
   Вместо отказа от хеша теперь чтение, и хеш считается по фактически
   прочитанным байтам.
3. **Процесс объявлялся только при `exec`.** Форкнутые воркеры, которые exec не
   делают (их используют make и cargo, и так же приходит каждый поток),
   накапливали чтения и записи под субъектом без типа `a b:process`. Все
   потребители графа ключуются на типе, поэтому **их рёбра молча отбрасывались:
   на сборке fzf это 1082 процесса из 1528, на cargo-сборке fd около трети**.
   Теперь процесс объявляется при создании, а разбор `.out` терпим к субъекту
   без типа, чтобы уже собранные трассы читались правильно.
4. **Пустой `/proc/<pid>/cmdline`.** У процесса, пойманного между `clone` и
   `exec`, командной строки ещё нет; запись NULL роняла трассировщик (SIGSEGV).
   Найдено при проверке пункта 3 и исправлено там же.

Первые три дефекта не видны на C-сборках вида «configure и make»: там процессы
почти всегда делают exec, потоки не умирают под нагрузкой, а sysfs не читают.
Именно поэтому эталон брался у другого прибора и на других языках.

## Ограничения этого захода

- Обёртка `cc` добавляет процесс на каждую компиляцию: это возмущение сборки,
  хоть и не влияющее на сравниваемые множества.
- Депфайлы не покрывают линковку, поэтому для стадии компоновки эталона нет;
  для неё пригодился бы `ld --trace`.
- Java не бралась намеренно: компиляция там идёт внутри процесса JVM, и результат
  известен заранее (ptrace не видит границ единиц трансляции). Это отдельный
  эксперимент про слепую зону, а не про сверку.
- Сборка в контейнере богаче минимального окружения, поэтому аудит
  `BuildRequires` на этих данных показывает больше «использовано без
  объявления», чем показал бы hasher с минимальным chroot.
